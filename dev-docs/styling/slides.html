01

Why styling is tricky

A OneCX page is a single document shared by the Shell, every MFE and every remote component. CSS, by default, does not know about any of those boundaries.

One page, many stylesheets

// the whole portal is ONE document
<body>
  <div class="onecx-shell"> ... Shell ... </div>
  <div data-style-id="product-a|app-a"> App A </div>
  <div data-style-id="product-b|app-b"> App B </div>
  <div data-style-id="mfe|x|mfe-y"> MFE ... </div>
</body>
Each app ships its own styles.css, component styles, and a PrimeNG/PrimeReact library that injects its own sheet into the same <head>.
The default: global
/* App A thinks it's alone */
.p-button {
  background: red;
}
:root {
  --p-primary: red;
}

With no isolation, .p-button and --p-primary apply to every .p-button on the page — Shell’s, App B’s, the MFE’s.

50+ stylesheets, one <head>. The entire problem this area solves: make each app’s rules apply only inside that app’s DOM subtree.

Four kinds of stylesheet

The same page carries sheets owned by different things. What matters is who owns it and whether it may leak.

KindOwnerSourceMay leak across scopes?
Application one MFE / RC styles.css + component CSS no — the whole point
Shell the Shell shell-styles.css no — scoped to shell-ui
Legacy portal-layout the Shell portal-layout-styles.css (static + dynamic) yes, but only to legacy (non-v6) apps
Shared theme / token the platform <link> global styles yes — genuinely global by design
Almost everything is scoped. Only the shared theme / token sheets are allowed to be truly global. Everything else is trapped inside an @scope block.
02

The @scope model

One CSS at-rule does the fencing. It confines a block of rules to a DOM region defined by a from selector and a to boundary.

One primitive: @scope

@scope([data-style-id="onecx-workspace|onecx-workspace-ui"]
        [data-no-portal-layout-styles])
   to ([data-style-isolation]) {

  :scope { --my-variable: red; }
  .my-class { color: red; }
}

@supports (@scope(...)) { ... } wraps the block as a fallback for browsers without native support.

from
Where the rules start applying — the element carrying data-style-id.
to
The boundary — rules stop at any element with data-style-isolation.
:scope
Names the opening element itself. :scope ≡ the from element.
It’s a selector boundary, not an inheritance reset. Rules can’t reach out, but CSS custom properties still inherit down across the boundary — a subtle and important distinction.

What the fence actually encloses

  • Inside the box → the block’s rules apply.
  • At a to element the block stops — nested isolation breaks the chain.
  • :scope variables are set on the from element, then inherit inward.
Both producers differ only in the from selector. Application styles use :is([data-no-portal-layout-styles], [data-mfe-element]); PrimeNG uses [data-no-portal-layout-styles] directly.

The boundary attributes

An app’s root element is annotated with a small set of data-* attributes. Each has one job.

<div
   data-style-id="product-a|app-a"
   data-no-portal-layout-styles
   data-mfe-element
   data-style-isolation
>
  ... app content ...
</div>
data-style-id
FROM — the scope id (product|app). Selects the scope’s root.
data-style-isolation
TO — a hard boundary the @scope block stops at.
data-no-portal-layout-styles
Opt-out of legacy styles; marks the app as libs-v6.
data-mfe-element
Marks an MFE element (alternative FROM trigger).
Pitfall: data-no-portal-layout-styles without data-style-id is a broken scope — there’s a boundary marker but no from selector to open the block.

The scope id: product | app

scopeIdFromProductNameAndAppId(
  'onecx-workspace',
  'onecx-workspace-ui',
)
→ 'onecx-workspace|onecx-workspace-ui'

One id, one subtree, one scope. The | joins the product and the application; MFEs carry the route between them.

Contextscope id
Workspace apponecx-workspace|onecx-workspace-ui
A remote componentrc-product|rc-app
An MFEmfe-product|mfe-app
Shellshell-ui (fixed)

The Shell is special: it opts out via SkipStyleScoping, so getScopeIdentifier() returns '' and the PrimeNG path targets the fixed shell-ui scope instead.

Nesting a remote component

An RC rendered inside an app gets its own scope. Two @scope blocks, two fences.

@scope([data-style-id="mfe-product|mfe-app"]
        [data-no-portal-layout-styles])
       to ([data-style-isolation]) {
  /* app rules */
}

@scope([data-style-id="rc-product|rc-app"]
        [data-no-portal-layout-styles])
       to ([data-style-isolation]) {
  /* rc rules */
}
Boundary is a fence, not a wall. The RC is a child of the app subtree, so the app’s --vars still flow in; the app’s rules simply don’t reach inside the RC.

Fence ≠ wall: variables still flow in

  • Rules (selectors) do not cross the boundary.
  • Custom properties inherit normally through it.
  • So a theme variable set higher up is still readable deep inside a nested scope.

This is why per-scope token renaming (Part 6) is needed for PrimeNG — shared --p- names would otherwise collide, not because of the fence but because of the inheritance.

04

Loading stylesheets on demand

App styles are fetched only when an app is actually rendered — and removed when the last use disappears. A usage counter drives both.

An app’s <style> element is marked up

<style
   data-app-styles="onecx-workspace|onecx-workspace-ui"
   data-mfe-styles
   data-slot-left-styles
   data-slot-footer-styles
>
  /* the app's styles.css, scoped */
</style>
data-app-styles
= the scope id. ≤1 per scope. Identifies the sheet.
data-mfe-styles
Present → the MFE uses this sheet. ≤1.
data-slot-<name>-styles
One per active slot that hosts an RC into this app. left, footer, …
Why the markers matter
The usage count is read straight off these attributes.

Usage counting drives load & removal

getStyleUsageCount(styleEl) {
  let n = 0;
  if (styleEl.hasAttribute('data-mfe-styles'))
    n++;
  for (const name of activeSlots(styleEl))
    n++;   // one per data-slot-*
  return n;
}

Load: fetchAppCss grabs <appUrl>/styles.css (returns nothing on failure → the element is removed). Add via useStyleForMfe / useStyleForRc.

usage count

0 → the <style> element is removed
MFE mounted slot: left RC slot: footer RC
Count ≥ 1: sheet stays loaded.
All uses gone → count 0: removeInactiveStyles drops the element.

Pitfalls: a shared app (MFE + RCs) uses the same sheet; on MFE switch the previous app is deregistered first; slot markers are per slot name, not per component; a destroyed Slot must release its use.

Who loads, and when

MFE → the Shell
routes.service.ts → updateAppStyles (a canActivateChild guard). Runs on every navigation into an app.
RC → SlotComponent
updateComponentStyles on slot fill; ngOnDestroy frees the slot marker.
function updateStyles(scopeId, url, isMfe) {
  if (isMfe)
    // deregister other apps' MFE use first
    removeAllMfeUsagesFromStyles(scopeId);

  let el = getAppStyleByScope(scopeId);
  if (el) { // already fetched
    useStyle(el); return;   // no 2nd fetch
  }

  el = createStyleUsedByMfeRc(scopeId);
  const css = await fetchAppCss(http, url);
  if (!css) { remove(el); return; }
  replaceStyleContent(el, createApplicationScopedCss(css));
}
Fetched exactly once per scope. fetchAppCss requests <appUrl>/styles.css with Accept: text/css; a missing / non-CSS response degrades to “no app styles” — the element is removed, no throw.
05

Frameworks

The scoping model is the same, but Angular and React reach it very differently. Two CSS kinds on the Angular side; a shared global sheet on the React side.

Angular: two kinds of CSS

Component styles

Per @Component, Angular’s emulated view encapsulation. The compiler adds attribute selectors:

/* compiled */
.p-button[_ngcontent-a1b2] {...}
[_nghost-x9] .title {...}

Scoped by attribute already — the isolation model re-binds the shared --p- vars these read.

Application styles

styles.css — the global app sheet. Only this goes through createApplicationScopedCss:

@scope([data-style-id="a|a"] ...) {
  :root → :scope
  ...
}

Plus Shell helpers wrap non-encapsulated component styles (@scope + onecxOriginalCss).

Only styles.css is the isolation-model sheet. Component CSS is scoped by the framework; the isolation model handles the app sheet and re-binds the tokens it reads.

React: a different shape

No view encapsulation

React doesn’t emit _ngcontent-. PrimeReact injects a global <style> instead:

<style data-primereact-style-id="button">
  .p-button {...}
</style>
So the libs scope it

scopeCss wraps it in the app’s @scope and a per-app StyleRegistry keeps the ids apart:

@scope([data-style-id="a|a"])
        to ([data-style-isolation]) {...}
themeStyleId = PRODUCT|PRODUCT
React consumes, it doesn’t fetch the same way — attachPrimeReactScoper + withAppStyles / withRemoteStyles do the per-app work.
06

PrimeNG & PrimeReact

Since PrimeNG 19 the library injects its own component CSS and design-token variables into <head> — assuming a single app. OneCX re-scopes both.

The PrimeNG collision

/* PrimeNG injects, per page: */
.p-button { background: var(--p-primary); }

:root {
  --p-primary: blue;
}

The library assumes one component-library instance per page and has no idea about the many apps on a OneCX page.

left global →

App A’s --p-primary and .p-button would restyle the Shell’s and App B’s components.

Two moves fix it: (1) wrap every injected sheet in the owning app’s @scope; (2) rename the token variables per scope so each app resolves its own copy.

Two moves: wrap, then rename

Move 1 — wrap in the app’s scope
@scope([data-style-id="a|a"]
        [data-no-portal-layout-styles])
       to ([data-style-isolation]) {
  :root → :scope
  --a-a-primary: blue;
  .p-button { background: var(--a-a-primary); }
}

Angular emits the @supports (@scope(...)) fallback on unsupported browsers; the Shell polyfill rewrites it.

Move 2 — rename --p- per scope
replacePrimengPrefix(css, "a|a")

--p-primary        →  --a-a-primary
--p-text-color    →  --a-a-text-color
/* non-alnum → '-' */

scopeIdentifierToVariablePrefix builds the prefix. Every <style> name gets -<scopeId> appended so the sheets stay distinct.

Angular: provideThemeConfig swaps PrimeNG’s UseStyle for CustomUseStyle, which runs scopePrimengCss(replaceRootWithScope(replacePrimengPrefix(css, id)), id). React: a per-app StyleRegistry + scopeCss do the same.

Under the hood: overriding UseStyle

provideThemeConfig swaps PrimeNG’s injector: { provide: UseStyle, useClass: CustomUseStyle }. The one method that matters is use():

use(css, options) {
  const id = getScopeIdentifier(options);
  const scoped =
    scopePrimengCss(
      replaceRootWithScope(
        replacePrimengPrefix(css, id)), id);
  options.name += `-${id}`;
  return super.use(scoped, options);
}
Three things per sheet
  • replacePrimengPrefix — --p- → --<id>-
  • replaceRootWithScope — :root → :scope
  • scopePrimengCss — wrap in @scope / @supports

Overrides → toVariables, written as a data-variable-override-id sheet last.

Per-scope tokens: three apps, three palettes

  • Each app resolves its own --<scopeId>- set.
  • The Shell uses the base --p- set — with SkipStyleScoping the id is '', so it’s not renamed.
  • Same .p-button class, different color per scope.
Same component-library class, isolated per app — because the tokens are renamed into non-colliding names and the rules are fenced by @scope.
07

Dynamic content (overlays)

Dialogs, pickers, tooltips often render into document.body — outside the app’s scoped subtree. Two routes keep them styled correctly.

The problem: an overlay escapes the scope

The dialog is a direct child of body. The app’s @scope block can’t reach it — so it renders unstyled.

Two fixes
A — patch the node at creation  ·  B — point it into an app-owned container

Two routes to keep the overlay scoped

Route A — via patching

Stamp the node at creation, promote at body.

Trigger element = last hovered/focused. cdk-overlay-container & cdk-visually-hidden are blacklisted from wrapping.

Route B — via container

Insert into an app-owned dynamic container.

CDK/Material via OnecxOverlayContainer + DYNAMIC_CONTAINER; PrimeNG via appendTo. The container is the boundary.

Route A under the hood: patching

A — intercept element creation

A build-time rewrite in each app routes framework element creation through document-level Shell helpers that stamp data-intermediate-style-* on the node at birth.

document.createOnecxElement (ensureCreateOnecxElement()) — legacy: createElementFromPrimeNg / …FromMaterial.
B — intercept document.body changes

Overwrite body.appendChild to wrap the node in a scope wrapper; overwrite body.removeChild to drop the wrapper and clean up.

Installed by dynamicContentInitializer() via ensureBodyChangesIncludeStyleData().
The takeaway

To render dynamic content we must intercept every element creation we can and every add/remove to document.body.

That means a source-code overwrite in every app, plus a global DOM patch — high-maintenance and risky.

⇒ prefer the dynamic-container path (Route B).

08

The @scope polyfill

@scope isn’t supported everywhere. The Shell installs a polyfill that rewrites the @supports (@scope(...)) fallback into plain CSS.

The rewrite: @scope → plain CSS

@supports (@scope([data-style-id="a|a"])
           to ([data-style-isolation])) {
  .custom-class { color: red; }
}

What Angular emits on a browser without native @scope.

/* after polyfill (performance) */
:where([data-style-id="a|a"]) {
  .custom-class
    :where(:nth-child(1) > :nth-child(2)) {
    color: red;
  }
}

The :nth-child path is the fingerprint of the rewrite.

Performance mode (default)
Rewrites each <style> once (observer on head). Fast — but rules can leak to same-named nodes.
Precision mode
Re-targets with exact :nth-child(n) paths; rewrites affected sheets on every DOM change (observer on body). Accurate — slower.
Guarded by typeof CSSScopeRule === 'undefined'. Un-nestable rules (@keyframes, @font-face) are lifted to the top instead of wrapped.

Pitfalls cheat sheet

Empty scope id (Shell)
The Shell resolves ''; don’t expect a --shell-ui- token prefix — it keeps base --p-.
Marker without data-style-id
data-no-portal-layout-styles alone is a boundary with no from selector to open the block.
html in a class name
:root/html → :scope is a plain string replace — a class literally named html breaks.
Nested same id
Two elements sharing a scope id make the from selector ambiguous.
Stale trigger (overlays)
Trigger = last hover/focus; programmatic overlays with no injector data inherit the wrong owner.
React emits a bare @scope
scopeCss writes a bare @scope(...), not the @supports wrapper — so the polyfill doesn’t rewrite it.

Recap

  • One fence: @scope(from) to (to) traps each sheet inside its app’s subtree; variables still inherit in.
  • Boundary = attributes: data-style-id, data-style-isolation, data-no-portal-layout-styles.
  • On demand: usage count → fetch styles.css, remove at zero.
  • PrimeNG: wrap and rename --p- per scope.
  • Overlays: patch at creation or insert into an app-owned container.
  • Polyfill: precision / performance rewrite of the @supports fallback.
