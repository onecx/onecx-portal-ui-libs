This Area explains where CSS on a OneCX page comes from and how the styles of the many applications that share a single page are kept apart. It is the fourth Area in the link:{dev-docs-index}[Dev Docs index].

toc::[]

== Problem

A single OneCX page hosts the Shell plus at least one Microfrontend, and often many Remote Components. Every one of those applications ships its own CSS, and a few shared stylesheets (theme variables, the Shell's own styles, legacy portal-layout rules) sit alongside them. Left unchecked, those stylesheets are global: a `button` rule from App A would restyle the buttons of App B and of the Shell.

The mechanism this Area covers keeps each application's styles bound to the content that belongs to it. It has three moving parts:

* A *scope* identifies the set of content owned by one application (the Shell, a Microfrontend, a Remote Component).
* Every stylesheet on the page except the genuinely global ones is *scoped* so its rules only apply inside the scope they belong to.
* Application stylesheets are *loaded on demand* when the application's content appears, and *removed* when the last use of them disappears.

The scoping primitive is the CSS https://developer.mozilla.org/en-US/docs/Web/CSS/@scope[@scope at-rule]. Because that rule is not supported in every browser, the Shell installs a polyfill (Unit 8) that rewrites scoped stylesheets when `@scope` is missing.

== Big picture

The work is split between the libraries in this repository and the Shell. The libraries provide the scope identifiers, the stylesheet utilities, and the Angular/React integration glue. The Shell owns the page-level initialisation: it starts the polyfill, loads the Shell's own and the legacy portal-layout stylesheets, and triggers the loading of Microfrontend styles on navigation.

The nine pages in this Area so far:

* *Why isolation & style kinds* (Unit 1) covers why isolation exists and the kinds of stylesheets that exist on a page; Unit 3 carries the detailed `@scope` model.
* *App/Remote Component stylesheet load & removal* (Unit 2) covers the load-on-demand and remove-on-unuse lifecycle with per-App/Slot usage counting.
* *`@scope` scoping model* (Unit 3) covers how the `@scope` at-rule binds an application's styles to its content, including nested Remote Components.
* *Shell's own stylesheets & legacy portal layout* (Unit 4) covers where the Shell's own and the legacy portal-layout stylesheets come from, how `styleInitializer` loads them, and how they are scoped.
* *Angular component styles* (Unit 5) covers how Angular component styles, already encapsulated by the compiler, fit into style isolation and where the model takes over for their shared variables.
* *Dynamic content via patching* (Unit 6) covers how an overlay or dialog rendered outside the app's scope is stamped at creation time, attributed from the trigger element, and then wrapped once it reaches `document.body`.
* *Dynamic content via container* (Unit 7) covers how out-of-scope content can instead be inserted into an app-owned dynamic container so it inherits the app's scope without being patched directly.
* *Scope polyfill* (Unit 8) covers how the Shell rewrites scoped stylesheets when the browser does not support `@scope`.
* *PrimeNG/PrimeReact style scoping* (Unit 9) covers how the component-library stylesheets PrimeNG and PrimeReact inject are wrapped in the owning application's scope and how its design-token variables are renamed per scope.

== Reading order

Start with Units 1 and 2 for the isolation problem statement and stylesheet categories, then read Unit 3 for the detailed `@scope` model and Unit 8 for the polyfill that rewrites it on browsers without native support. The Shell's own stylesheets, component styles, dynamic content patching, dynamic-container insertion, and PrimeNG variable scoping build on the same scope ids and attributes and are the natural next steps.
