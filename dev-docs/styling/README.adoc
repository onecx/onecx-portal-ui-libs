This Area explains where CSS on a OneCX page comes from and how the styles of the many applications that share a single page are kept apart. It is the fourth Area in the link:{dev-docs-index}[Dev Docs index].

toc::[]

== Problem

A single OneCX page hosts the Shell plus at least one Microfrontend, and often many Remote Components. Every one of those applications ships its own CSS, and a few shared stylesheets (theme variables, the Shell's own styles, legacy portal-layout rules) sit alongside them. Left unchecked, those stylesheets are global: a `button` rule from App A would restyle the buttons of App B and of the Shell.

The mechanism this Area covers keeps each application's styles bound to the content that belongs to it. It has three moving parts:

* A *scope* identifies the set of content owned by one application (the Shell, a Microfrontend, a Remote Component).
* Every stylesheet on the page except the genuinely global ones is *scoped* so its rules only apply inside the scope they belong to.
* Application stylesheets are *loaded on demand* when the application's content appears, and *removed* when the last use of them disappears.

The scoping primitive is the CSS https://developer.mozilla.org/en-US/docs/Web/CSS/@scope[@scope at-rule]. Because that rule is not supported in every browser, the Shell installs a polyfill (Unit 8) that rewrites scoped stylesheets when `@scope` is missing.

== Big picture

The work is split between the libraries in this repository and the Shell. The libraries provide the scope identifiers, the stylesheet utilities, and the Angular/React integration glue. The Shell owns the page-level initialisation: it starts the polyfill, loads the Shell's own and the legacy portal-layout stylesheets, and triggers the loading of Microfrontend styles on navigation.
