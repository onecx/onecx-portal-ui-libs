== Question answered

Why does OneCX need style isolation at all, and what kinds of stylesheets exist on a OneCX page?

== Why it exists

A OneCX page is not a single application. It hosts the Shell, at least one Microfrontend, and possibly many Remote Components, each of which is a separately built application that ships its own CSS. Browsers treat `<style>` and linked stylesheets as global: every rule applies to the whole document unless told otherwise. So a `h1 { margin: 0 }` in one application would quietly restyle the headers of every other application on the page.

Style isolation is the answer to that coupling. The idea is: *each application is responsible for styling its own content, and none of its CSS leaks into content it does not own.* This has been a design goal since libs version 6. The Shell is the only application whose styles are expected to be visible across the page, and even those are confined to Shell-owned content.

Two mechanisms make it possible:

* A *scope identifier* marks the content that belongs to one application, so the rules that apply there can be addressed precisely.
* The CSS {scope_at_rule} at-rule, which lets a stylesheet declare "these rules only apply between `<from>` and `<to>`" so that the application's rules stop where its content ends.

Because {scope_at_rule} is not supported in every browser, the Shell runs a polyfill (Unit 8) that rewrites the scoped rules when the native rule is absent.

== How it works

=== Scope identifiers

Every piece of scoped content is anchored to a *scope id*. The id is derived from the application that owns the content and has the form `productName|appId`. The Shell uses a fixed id `shell-ui`.

link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`] defines both the derivation and the HTML attributes that carry the scope. The relevant pieces:

* `scopeIdFromProductNameAndAppId(productName, appId)` builds the `productName|appId` id.
* `getScopeIdentifier(appStateService, skipStyleScoping, remoteComponentConfig)` resolves the id for the content being styled. For a Remote Component it reads the component's config; for a Microfrontend it reads the current-MFE topic. For the Shell it returns an empty id because the Shell opts out of per-app scoping (`SKIP_STYLE_SCOPING` is provided as `true` in the Shell).

A content element is recognised as the *start* of a scoped section by the `data-style-id` attribute, and the section *ends* at the next element with `data-style-isolation`. Two optional attributes refine the behaviour:

[cols="1,3", options="header"]
|===
|Attribute |Meaning

|`data-style-id`
|Start of the scope section, carries the scope id.

|`data-style-isolation`
|End of the scope section. From this element on, the parent's styles no longer apply to its children.

|`data-no-portal-layout-styles`
|This scope does not want the legacy portal-layout rules. Paired with `data-style-id`; its presence marks the content as libs v6+ compatible.

|`data-mfe-element`
|Marks the Microfrontend's content specifically, used to preserve the (legacy) behaviour where app styles applied only to the MFE and not to its Remote Components.
|===

A scoped stylesheet then targets the section with an {scope_at_rule} block, for example:

[source,css]
----
@scope([data-style-id="onecx-workspace|onecx-workspace-ui"][data-no-portal-layout-styles])
     to ([data-style-isolation]) {
  :scope { --my-variable: red; }
  .my-class { color: red; }
}
----

Inside the block, `:scope` refers to the element that opened the scope, so `:root`-level rules in the application's own CSS are rewritten to `:scope` before the block is emitted. `createApplicationScopedCss` in link:{libs}/angular-utils/style/src/utils/app-styles-scope.utils.ts[`app-styles-scope.utils.ts`] performs that rewrite (via `replaceRootAndHtmlWithScope`) and wraps the CSS in the `@scope`/`@supports` block.

=== CSS variables vs other rules

Variables and ordinary rules are scoped slightly differently. A CSS variable that must not be visible outside its scope is wrapped in the `@scope` block and set on `:scope`. Ordinary rules are wrapped in the same `@scope` block with no extra wrapping. The polyfill treats the two the same when rewriting, because both sit inside the `@scope` boundary.

== Libs side / Shell side

=== Libs side

The libraries provide the scope vocabulary and the utilities that consume it:

* link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`] — the scope id derivation, the `data-style-*` / `data-intermediate-*` attribute constants, `isCssScopeRuleSupported()`, and the PrimeNG helpers `scopePrimengCss` and `replacePrimengPrefix` (which renames PrimeNG's `--p-` variables to be unique per scope, via `scopeIdentifierToVariablePrefix`).
* link:{libs}/angular-utils/style/src/utils/app-styles-scope.utils.ts[`app-styles-scope.utils.ts`] — `createApplicationScopedCss`, which turns an application's raw CSS into a scoped `@scope` block, and `getAppStyleByScope`, which finds the already-loaded `<style>` element for a scope.
* The `angular-utils/style` package (link:{libs}/angular-utils/style/src/api/constants.ts[`constants.ts`]) — the attributes that mark *stylesheets* (`data-app-styles`, `data-mfe-styles`, `data-slot-<name>-styles`, `data-shell-styles`), distinct from the attributes that mark *content*.

=== Shell side

The Shell owns the page-level styles and the polyfill:

* link:{shell}/src/app/app.module.ts[`app.module.ts`] — `styleInitializer` selects the polyfill mode (`POLYFILL_SCOPE_MODE`, defaulting to performance mode) and loads the Shell's own and the legacy portal-layout stylesheets. It also provides `SKIP_STYLE_SCOPING` as `true`, which is why the Shell's content is not treated as one of the scoped applications.
* link:{shell}/src/app/shell/utils/styles/shell-styles.utils.ts[`shell-styles.utils.ts`] — loads the Shell's `shell-styles.css` and scopes it to the `shell-ui` id.
* link:{shell}/src/app/shell/utils/styles/legacy-style.utils.ts[`legacy-style.utils.ts`] — loads the legacy `portal-layout-styles.css` as two scoped sheets (`data-portal-layout-styles` and `data-dynamic-content-portal-layout-styles`), scoped to *not* the v6-migrated scopes.
* link:{shell}/src/scope-polyfill/polyfill.ts[`scope-polyfill/polyfill.ts`] — the polyfill that rewrites scoped stylesheets when the browser lacks {scope_at_rule}.

== Angular / React

The scope *model* is identical in both frameworks: the same `data-style-id` / `data-style-isolation` attributes and the same `@scope`-wrapped stylesheets. What differs is how the CSS is placed.

* *Angular:* `scopePrimengCss` and `createApplicationScopedCss` produce the scoped CSS; PrimeNG stylesheets are scoped by the Angular theme provider (Unit 9).
* *React:* PrimeReact styles are scoped by a per-app `MutationObserver` (link:{libs}/react-utils/src/lib/styling/primeReact/scopingFunctionality/index.ts[`attachPrimeReactScoper`]) that writes scoped copies of the PrimeReact blocks into a dedicated `<style data-app-primereact-style="…">`, and theme variables are applied onto the existing app stylesheet by link:{libs}/react-utils/src/lib/styling/primeReact/theme/applyThemeVariables.ts[`applyThemeVariables`]. The HOCs `withApp`/`withRemote` (link:{libs}/react-utils/src/lib/styling/primeReact/hocs/withApp/index.ts[`withApp`], link:{libs}/react-utils/src/lib/styling/primeReact/hocs/withRemote/index.ts[`withRemote`]) wire these providers in.

== Edge cases & pitfalls

* *Empty scope id.* `getScopeIdentifier` returns `''` when scoping is skipped (the Shell). Helpers such as `replacePrimengPrefix` treat an empty id as "do nothing", so Shell content is not prefixed or scoped by the per-app rules.
* *`data-no-portal-layout-styles` without `data-style-id`.* The no-portal-layout marker only makes sense paired with `data-style-id`; the legacy portal-layout sheets target `[data-style-id]:not([data-no-portal-layout-styles])`, so a scope without a `data-style-id` is not addressed by them.
* *Variables leaking via the wrong wrapping.* A variable that is not wrapped in the `@scope` block (or set on `:scope`) becomes global. Wrapping matters, not just the attribute.
* *Browser without {scope_at_rule}.* All of the above only holds if the polyfill has run. In performance mode the Shell may allow a small amount of leakage to stay fast; in precision mode it rewrites every affected rule (Unit 8).

== Debugging

Open the page and inspect the `<head>`:

* `<style data-app-styles="productName|appId">` — an application's loaded stylesheet (Unit 2).
* `<style data-mfe-styles>`, `<style data-slot-<name>-styles>` — usage markers showing which MFE/Slot the sheet is active for.
* `<style data-shell-styles>`, `<style data-portal-layout-styles>` — Shell and legacy sheets.
* The content elements carry `data-style-id` / `data-style-isolation`. Check that the id on a `data-style-id` element matches the `data-app-styles` value you expect.

The libs log under the namespaces `scope.utils` and `fetch-app-css` when a scope id cannot be built or a `styles.css` cannot be fetched. General runtime inspection is covered by the *Diagnostics* Area.

== Known issues

* In performance polyfill mode the Shell deliberately allows some cross-scope leakage to keep the page fast. If a rule from one application visibly affects another on a browser without native {scope_at_rule}, check `POLYFILL_SCOPE_MODE` (link:{shell}/src/app/app.module.ts[`app.module.ts`]) — precision mode rewrites per-element and is the accurate path.
