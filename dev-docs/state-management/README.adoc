This Area explains how an App keeps an NgRx store in step with the rest of a OneCX page: how the Shell context that the Shell publishes is wired into an NgRx store, how App state that must survive a URL is serialised into the URL, and how App state is persisted and rehydrated across reloads. It covers NgRx only: the libraries in this repository expose NgRx-specific connectors and helpers; the React side has no store-equivalent here.

toc::[]

== Problem

An App does not live in isolation. It runs inside a Shell together with the other Micro Front Ends, all of them reading the same Shell context and the same `window.location`. Yet an NgRx App keeps its state in a store that lives inside the App. Nothing, by itself, keeps those two worlds in sync:

* The Shell publishes context (workspace, configuration, permissions, current MFE, current location, current theme, …) over Topics. An NgRx App wants that data in its *store*, not only as a service `Observable`.
* A URL change can happen without the App's involvement (the Shell navigating, the browser back/forward button). An App whose state is derived from the URL needs a reliable way to read and write that slice of the URL.
* A reload or a fresh tab discards the store. App-specific state that must survive this (a selected filter, a tab that was open) has to be persisted to `localStorage` and rehydrated: but an App may load its feature reducers lazily, so the rehydration step cannot blindly overwrite slices that are not loaded yet.

These are three different problems. The first is a *connection* between the Shell and the store; the second is a *round-trip* between the store and the URL; the third is a *round-trip* between the store and `localStorage`. The Units below cover each one.

== Big picture

The Shell is the publisher of the context that the store needs. The libraries in this repository do two things. First, `ngrx-integration-interface` turns the Shell's context Topics into an NgRx slice: it defines the state shape, the actions, the reducer and the selectors, and ships one *store connector* service per piece of context that subscribes to the underlying Angular service/Topic and dispatches into the store. Second, `ngrx-accelerator` provides the framework-level helpers for the other two round-trips: the URL-synced state helpers (fragment-parameters) and the `localStorage` rehydration helpers (lazy-loading merge reducer and key configuration).

[source,mermaid]
----
flowchart LR
  subgraph Shell
    PUB[Shell publishes context Topics]
    NAV[Shell drives the URL / current-location]
  end
  subgraph Topics
    CTX[context Topics]
    URL[window.location / current-location]
  end
  subgraph App
    CONN[store connectors]
    STORE[(onecx store slice)]
    FRAG[fragment-params helpers]
    LS[localStorage rehydration helpers]
  end
  PUB --> CTX --> CONN
  NAV --> URL --> CONN
  CTX --> URL
  CONN --> STORE
  STORE <--> FRAG
  STORE <--> LS
  LS -.-> |persist / rehydrate| LS2[(localStorage)]
----

Reading it: the Shell publishes the context Topics and drives navigation / `current-location`; the store connectors turn both into `OneCxActions` dispatched into the `onecx` slice; the fragment-params helpers keep a URL-derived slice of state in sync with `window.location`, and App code can also update the shared URL through those helpers; the `localStorage` helpers persist and rehydrate App state across reloads. The Shell never touches the store directly: it is the publisher of the context, while URL updates can come from either the Shell or an App, and everything else is App-side wiring.

The Shell-side details (which Topics exist, when they are ready, how the URL is shared and activated) are not re-explained here. They belong to the other Areas: Area 3 (Shell Context & Runtime Configuration) for the context Topics, and Area 7 (Navigation & Routing) for the shared URL and `current-location`. This Area only describes what the NgRx side does with them.
