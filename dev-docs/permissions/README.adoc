== Problem

OneCX decides what a user may see and do from permission *keys*. The Shell is the only component that knows those keys for the whole session, while every App and every Remote Component has to act on them. This Area explains how the permission data moves from the Shell to the rest of the page, and how the pieces on each side fit together:

* how the Shell loads and caches the permission lists it serves, and
* how Apps and Remote Components receive and check them.

The data structures are framework-agnostic: the contract lives in the `@onecx/integration-interface` package of this repository, and the Shell talks to the same Topics from the other side. The Units below explain one question each; read them in the order listed under Unit map.

== Big picture

The Shell owns the permission data. It loads a user's permission list from its backend, caches it, and pushes it out over two Topics. Apps subscribe to the push Topic to get the permissions for the application that is currently in the foreground, while Remote Components use the request/response (RPC) Topic to ask for the permissions of *another* application.

Two repositories share the work. The *libs* define the Topics and the clients that consume them (see the link:{libs}/integration-interface/src/lib/topics/permissions/v1/permissions.topic.ts[Topics] and the `UserService` / Remote Component services). The *Shell* loads, caches and publishes the data (`link:{shell}/src/app/shell/services/permissions-cache.service.ts[PermissionsCacheService]`, `link:{shell}/src/app/shell/services/routes.service.ts[RoutesService]`, `link:{shell}/src/app/shell/services/permission-proxy.service.ts[PermissionProxyService]`). Every Unit below names the files on both sides it relies on.
