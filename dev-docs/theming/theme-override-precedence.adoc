= Theme Overrides: CSS vs PrimeNG overrides and their precedence
:idprefix:
:idseparator: -
:libs: ../../libs
:shell: https://github.com/onecx/onecx-shell-ui/blob/main

:shell_wrapping_utils: https://github.com/onecx/onecx-shell-ui/blob/main/src/app/shell/utils/styles/update-required-wrapping-styles.utils.ts
:theme_overrides_guide: https://onecx.github.io/docs/guides/current/angular/theming.html#theme-overrides
:overview: ./overview.adoc

Theme overrides let a OneCX application adjust the appearance of the PrimeNG / PrimeReact components it renders, on top of the Workspace theme the libraries and Shell have already applied. This Unit covers the three override paths, Workspace *raw CSS overrides*, application *CSS-variable overrides*, and *PrimeNG design-token (preset) overrides*, and the precedence rules between them and against the default theme. It is the third Unit of the *Theming & Visual Assets* Area.

== Question answered

When a component's look can come from the default preset, from the Workspace theme, and from the application's overrides, which value wins: and by what mechanism?

== Why it exists

The Workspace theme is mapped onto PrimeNG design tokens through the OneCX preset (see the *Theme → PrimeNG / PrimeReact tokens* Unit). That mapping covers the tokens OneCX knows about, but it cannot cover every token a component uses, and each application has its own visual requirements. An application therefore needs a way to nudge individual values without rebuilding the whole preset.

Three override paths are available, and they operate at different points of the theming pipeline:

* **Workspace CSS overrides**: raw CSS strings stored in `Theme.overrides` entries with `type === CSS`. The Shell appends each non-empty string to `document.head` as its own `<style>` element. This path is not automatically scoped, so it competes through the ordinary CSS cascade.
* **Application CSS-variable overrides**: application-provided override values (not raw CSS). These values are supplied via `provideThemeConfig({ overrides })` and `CustomUseStyle` converts them (via PrimeUIX `toVariables`) into scoped CSS written into a `<style>` element. They compete with PrimeNG's generated CSS variables through the normal CSS cascade, but only inside the owning scope.
* **PrimeNG / token overrides**: Workspace `Theme.overrides` entries with `type === PRIMENG`, folded into the preset before PrimeNG computes any CSS. They change the token at the source, so no cascade is involved.

Only the application CSS-variable path is scoped per application. Workspace CSS overrides are global to the page unless the CSS text scopes itself.

== How it works

The three paths are fed from **different sources** and win by different mechanisms:

* the **Workspace CSS channel** is fed by the *Workspace theme*: the `Theme` object carries an optional `overrides` list (link:{libs}/integration-interface/src/lib/topics/current-theme/v1/theme.model.ts[`Theme.overrides`], of type link:{libs}/integration-interface/src/lib/topics/current-theme/v1/theme-override.model.ts[`ThemeOverride`], each entry a `type` + a string `value`), and the Shell filters that list for `type === OverrideType.CSS` in link:{shell_app_module}[`src/app/app.module.ts`];
* the **application CSS-variable channel** is fed by the *application*: the override values are supplied through `provideThemeConfig({ overrides })` (the `THEME_OVERRIDES` injection token, see link:{libs}/angular-utils/theme/primeng/src/utils/application-config.ts[`application-config.ts`]) and applied by `CustomUseStyle`;
* the **PrimeNG / token channel** is also fed by the *Workspace theme*: `ThemeConfigService` folds the `PRIMENG`-typed entries into the preset.

The shared contract (link:{libs}/integration-interface/src/lib/topics/current-theme/v1/theme-override.model.ts[`OverrideType`]) defines both a `PRIMENG` and a `CSS` entry type. The Shell consumes the `CSS` entries directly, while the libraries only ever filter `Theme.overrides` for `type === OverrideType.PRIMENG` (link:{libs}/angular-utils/theme/primeng/src/services/theme-config.service.ts[`parsePrimeNGOverridesValue`]); the application CSS-variable channel is driven by the application's `THEME_OVERRIDES` token rather than by `CSS`-typed entries of `Theme.overrides`.

|===
|Channel |Source |Precedence mechanism |Angular entry point

|Workspace CSS override

|Ordinary CSS cascade. The Shell appends each non-empty raw CSS string as a `<style>` in `<head>`, but it is not auto-scoped or guaranteed to outrank every generated style; specificity and the current DOM order decide conflicts.
|link:{shell_app_module}[`applyThemeVariables` in `src/app/app.module.ts`]

|Application CSS-variable override

The three paths take different inputs and rejoin at the rendered values, but by different routes:

[source,mermaid]
----
flowchart LR
  W["Theme.overrides (type = CSS)"] --> W1["Shell CSS channel"]
  A["App: provideThemeConfig overrides / THEME_OVERRIDES"] --> C1["Application CSS-variable channel"]
  T["Theme.overrides (type = PRIMENG)"] --> T1["PrimeNG / token channel"]
  W1 --> W2["unscoped style element appended to head"]
  C1 --> C2["scoped style element, re-appended last in head"]
  T1 --> T2["mergeDeep into preset, before PrimeNG derives CSS"]
  W2 -. "ordinary cascade: specificity + current DOM order" .-> P["Rendered values"]
  C2 -. "same specificity, later in DOM wins" .-> P["Rendered values"]
  T2 -. "token value set at the source" .-> P
----

[#workspace-css-channel]
=== Workspace CSS channel (Shell-owned raw CSS)

When the Shell receives the Workspace theme, link:{shell_app_module}[`applyThemeVariables` in `src/app/app.module.ts`] publishes the theme, applies `theme.properties` as document-level CSS variables, then filters `theme.overrides` for `type === OverrideType.CSS`. For each override whose `value` is non-empty, it creates a fresh `<style>`, sets `data-css-overrides` and `data-marked-as-wrapped`, appends the raw string, and appends the element to `document.head`.

That `data-marked-as-wrapped` marker matters: link:{shell_wrapping_utils}[`update-required-wrapping-styles.utils.ts`] only wraps styles marked `data-marked-for-wrapping`, and treats `data-marked-as-wrapped` as already handled. So this Shell path does **not** get the automatic `@scope` wrapping used elsewhere. Its precedence is therefore just ordinary CSS cascade behaviour: the winning rule depends on selector specificity and on the DOM order of the style elements at the time the browser evaluates them. A Shell CSS override can beat generated styles, but it does not universally outrank them.

[#css-channel]
=== Application CSS-variable channel (DOM-order precedence)

Every PrimeNG stylesheet is created through the `UseStyle` service, which OneCX replaces with link:{libs}/angular-utils/theme/primeng/src/services/custom-use-style.service.ts[`CustomUseStyle`]. On each stylesheet update `CustomUseStyle` resolves the application's overrides and, in link:{libs}/angular-utils/theme/primeng/src/services/custom-use-style.service.ts[`applyOverrides`], turns them into CSS with PrimeUIX `toVariables`, scopes that CSS for the current application, and writes it into a single `<style data-variable-override-id="<scopeId>">` element (one per scope, created or retrieved by link:{libs}/angular-utils/theme/primeng/src/services/custom-use-style.service.ts[`createOrRetrieveOverrideElement`]).

The element is then re-appended to the end of the document head: the code comment says *"Always make sure it is the last child of the document head."* PrimeNG's own stylesheets and this override `<style>` define the same scoped CSS variables with the same specificity, so in the CSS cascade the element that comes later in the DOM wins. Re-appending the override `<style>` last on every update is what gives overrides their precedence over the default theme and over PrimeNG's default token values.

[#primeng-channel]
=== PrimeNG / token channel (preset folding)

On every `CurrentThemeTopic` change, link:{libs}/angular-utils/theme/primeng/src/services/theme-config.service.ts[`ThemeConfigService.applyThemeVariables`] rebuilds the effective preset. When advanced theming is enabled, it first selects the entries whose `type === OverrideType.PRIMENG`, JSON-parses their `value`, and `mergeDeep`-reduces them into one object (link:{libs}/angular-utils/theme/primeng/src/services/theme-config.service.ts[`parsePrimeNGOverridesValue`] and `foldOverrides`). That folded object is the *last* argument of the preset merge:

[source,typescript]
----
preset = mergeDeep(preset, mergeDeep(themeConfig.getConfig(), overridesFolded))
----

Because `mergeDeep` gives the later argument priority, the folded overrides win over the theme values for the same token key. The result is passed to PrimeNG via `setThemeConfig`, so PrimeNG derives its CSS variables from the *already-overridden* tokens: the override is baked in rather than fought over in the cascade.

The application CSS-variable and PrimeNG / token channels are scoped through the same helpers in link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`] (`scopePrimengCss`, `replacePrimengPrefix`, `dataVariableOverrideIdAttribute`), so an override in one application never affects another. The Shell Workspace CSS path bypasses those helpers and remains whatever scope the raw CSS itself expresses.

== Libs side / Shell side

=== Libs side

The libraries own the application CSS-variable and PrimeNG / token mechanisms:

* link:{libs}/angular-utils/theme/primeng/src/services/custom-use-style.service.ts[`CustomUseStyle`]: scopes and appends the CSS-variable override `<style>` last in `<head>`.
* link:{libs}/angular-utils/theme/primeng/src/utils/application-config.ts[`application-config.ts`]: the `THEME_OVERRIDES` injection token and the `provideThemeConfig({ overrides, isAdvancedTheming })` entry point.
* link:{libs}/angular-utils/theme/primeng/src/services/theme-config.service.ts[`theme-config.service.ts`]: `ThemeConfigService` folds `PRIMENG`-typed overrides into the preset, gated by `IS_ADVANCED_THEMING`.
* link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`]: the scoping helpers and the `data-variable-override-id` attribute that identify the override element.

The `ThemeOverride` / `OverrideType` contract is defined in link:{libs}/integration-interface/src/lib/topics/current-theme/v1/theme-override.model.ts[`theme-override.model.ts`] and carried on the `CurrentThemeTopic`.

=== Shell side

The Shell is the page host: it owns the shared `<head>` in which every application's scoped override `<style>` lands, and it is itself one scope (scope id `shell-ui`, see `shellScopeId` in link:{libs}/angular-utils/src/lib/utils/scope.utils.ts[`scope.utils.ts`]). It also owns the Workspace CSS-entry insertion path: in link:{shell_app_module}[`src/app/app.module.ts`] it consumes Workspace `Theme.overrides` entries with `type === CSS`, creates raw `<style data-css-overrides data-marked-as-wrapped>` elements, and appends them to `document.head`.

Because those elements are marked as already wrapped, link:{shell_wrapping_utils}[`src/app/shell/utils/styles/update-required-wrapping-styles.utils.ts`] does not scope them automatically. The Shell therefore participates in override handling in two ways: it hosts the libraries' scoped application overrides, and it directly injects the Workspace's raw CSS overrides. The first stage of the flow (putting the Workspace theme's CSS variables, favicon and logo on the page) is covered by the *Theme → page* Unit.

== Angular / React

=== Angular

The libraries' application CSS-variable path and PrimeNG / token path are Angular-only. An application calls link:{libs}/angular-utils/theme/primeng/src/utils/application-config.ts[`provideThemeConfig({ overrides })`]; `overrides` may be a plain value, a `Promise`, or a factory function (resolved with `runInInjectionContext`, so the factory runs in the correct injection context). Setting `isAdvancedTheming: true` also switches on the PRIMENG / token channel via `IS_ADVANCED_THEMING`. The Workspace CSS path described above is implemented by the Angular Shell in link:{shell_app_module}[`src/app/app.module.ts`].

=== React

The libraries' override mechanism is **Angular-only**. PrimeReact theming is driven by link:{libs}/react-utils/src/lib/styling/primeReact/theme/applyThemeVariables.ts[`applyThemeVariables`], which maps `theme.properties` into `--app-*` custom properties inside an `@layer tokens` block. It reads `theme.properties` only, it does *not* read `theme.overrides`, and there is no `CustomUseStyle` equivalent, so the libraries do not apply theme overrides for React. (React still defines the shared `dataVariableOverrideIdAttribute` constant in link:{libs}/react-utils/src/lib/utils/styleAttributes.ts[`styleAttributes.ts`], but nothing in the React path applies it. A React application can of course inject its own CSS, but that is the application's own styling, not a OneCX theme-override feature.)

== Edge cases & pitfalls

* **Token overrides are opt-in and silently dropped otherwise.** When `IS_ADVANCED_THEMING` is `false` (the default), `applyThemeVariables` sets `overridesFolded` to `{}`, so `PRIMENG`-typed overrides have no effect even though they are present on the `Theme`. The Workspace CSS channel and the application CSS-variable channel are unaffected by that flag.
* **Empty CSS inputs are no-ops, but via different checks.** The Shell only appends Workspace CSS overrides whose raw `value` is truthy. `CustomUseStyle.applyOverrides` returns without touching the DOM when the resolved application override produces no variables (`variablesData.value.length === 0`). In the application path, this early return does not remove or replace an existing scoped override `<style>` element: any previously-applied scoped styles remain active for that scope.
* **One override `<style>` per scope.** All updates for a scope write into the same `<style data-variable-override-id="<scopeId>">`, re-appended last each time. On a multi-application page each scope keeps its own element, so overrides stay isolated.
* **Only the application CSS-variable channel is auto-scoped.** The application override CSS is wrapped with `@scope` (or `@supports (@scope …)` when the browser lacks `@scope`), so it only applies inside the owning scope. The Shell's Workspace CSS path is not auto-scoped.
* **`mergeDeep` returns a new object and does not mutate its inputs.** The folding of token overrides uses `mergeDeep` to build a merged preset object that gives later arguments priority without mutating the original preset or theme objects.

== Debugging

* The logger namespace is `CustomUseStyle` (see `createLogger` in link:{libs}/angular-utils/theme/primeng/src/utils/logger.utils.ts[`logger.utils.ts`]).
* For Workspace CSS overrides, inspect `<head>` for `style[data-css-overrides]`. Those elements come from the Shell path and are marked `data-marked-as-wrapped`.
* In the page, inspect `<head>` for `style[data-variable-override-id="<scopeId>"]`. Its presence, its position (it should be among the last `<style>` elements) and its text content show the effective CSS overrides.
* Reading the `name` or `el` property of `CustomUseStyle.use`'s return value logs an error by design: that is a signal a consumer is misusing the API, not a theming fault.
* To confirm which value won for a component, inspect the computed style and the matching rules: application CSS-variable overrides usually win by being re-appended last with equal specificity, while Shell Workspace CSS overrides win or lose according to selector specificity and current DOM order.
