This Area explains how OneCX places *Remote Components* into *Slots*: how the Workspace decides which component goes into which slot, and how that component is actually rendered on the page.

toc::[]

== Problem

A portal page is made up of many independently built micro-frontends (MFEs), but a user expects to see a single coherent layout — a header, a menu, a footer, and small widgets dropped into reserved regions of that layout. Some of those widgets are not Apps: they are small, self-contained UI pieces (a toast, a header badge, an inline panel) that one MFE exposes and another host MFE or the Shell renders in a reserved place.

That requires a mechanism with two answers:

* *Which* component fills a given region of the page?
* *How* is that component instantiated and wired up once it is chosen?

This Area covers both. Bootstrap of a Remote Component, its styles, its permissions and its translations are owned by other Areas and are only linked to from here.

== Big picture

The work is split between the libraries in this repository and the Shell.

The Shell loads the *Workspace configuration* from the BFF, which contains a list of Remote Components and a list of Slots that assign components to named regions. After normalising legacy slot names, the Shell publishes that data to every MFE on the page through the link:{libs}/integration-interface/src/lib/topics/remote-components/v1/remote-components.topic.ts[`RemoteComponentsTopic`].

Each MFE that wants to host a widget renders one or more slot elements — `<ocx-slot>` in Angular and `SlotComponent` in React. The slot service in the MFE reads the published data, resolves the component names for its slot, loads the component's code through Module Federation, and renders it.

[source,mermaid]
----
flowchart LR
  BFF["Shell BFF<br/>(workspace config)"] --> SHELL
  subgraph SHELL["OneCX Shell"]
    direction TB
    WC["workspaceConfigInitializer<br/>loads workspace config"]
    MAP["mapSlots()<br/>normalises legacy slot names"]
    PUB["RemoteComponentsTopic.publish<br/>{ components, slots }"]
    WC --> MAP --> PUB
  end
  PUB -->|topic: remoteComponentsInfo| MFE
  subgraph MFE["Host MFE"]
    direction TB
    SVC["SlotService.getComponentsForSlot<br/>(or SlotProvider / useSlot)"]
    MF["Module Federation<br/>loads the remote module"]
    SLOT["slot element<br/>&lt;ocx-slot&gt; / &lt;SlotComponent&gt;"]
    SVC --> MF --> SLOT
  end
  SLOT --> RC["Remote Component<br/>instance rendered into the slot"]
----

The data the Shell publishes is defined in the libs. A `Slot` maps a slot name to the names of the Remote Components assigned to it, and a `RemoteComponent` carries its identity (`appId`, `productName`), how to load it (`remoteEntryUrl`, `exposedModule`) and its `technology` (see link:{libs}/integration-interface/src/lib/topics/remote-components/v1/remote-component.model.ts[`remote-component.model.ts`]).
