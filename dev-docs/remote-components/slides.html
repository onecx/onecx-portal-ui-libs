Slot ↔ Remote Component

Who is involved and who does what

The cast

Who does what

Shell

  • loads Workspace config
  • normalises legacy slot names
  • publishes RemoteComponentsTopic
  • answers permission RPC
  • hosts its own slot groups

Host page

  • places <ocx-slot name>
  • provides SLOT_SERVICE
  • passes inputs / outputs
  • optional: isSomeComponent­DefinedForSlot → fallback UI

Slot (libs)

  • name → components
  • loads via MF
  • asks permissions
  • keeps order (spans)
  • hands over config
  • scopes styles
  • reports size

Remote Component

  • implements the config contract
  • keeps baseUrl
  • declares inputs / outputs
  • calls its own BFF
  • own translations

Nobody hard-codes the RC. The Workspace decides what goes where.

What the RC does with its config

workspace-data.component.ts

export class OneCXWorkspaceDataComponent
  implements ocxRemoteComponent, ocxRemoteWebcomponent {

  @Input() set ocxRemoteComponentConfig(c) {
    this.ocxInitRemoteComponent(c)       // WC flavour → same path
  }

  ocxInitRemoteComponent(config: RemoteComponentConfig) {
    this.baseUrl.next(config.baseUrl)      // → translations loader
    this.workspaceApi.configuration = new Configuration({
      basePath: join(config.baseUrl, apiPrefix) // → own BFF
    })
  }
}
1. both contracts → any host
2. baseUrl → ReplaySubject → late readers OK
3. BFF calls relative to own origin
4. i18n: provideTranslationPathFromMeta(import.meta.url) (newer way)

Style lifecycle

Styles are counted per slot

1. RC created in slot A → fetch + add sheet

3. slot A destroyed → sheet stays

Pitfalls cheat sheet

🔇 RC implements neither contract → no config, no error
🏷️ web component without elementName → not rendered
🔤 typo in input / output name → silently ignored
⚛️ React host + Angular RC → error, not rendered
💉 REMOTE_COMPONENT_CONFIG → RC must provide it
🧩 SLOT_SERVICE missing in host → slot stays empty
📏 no requestEvent → no size events
🎨 CSS variables cross the isolation boundary
