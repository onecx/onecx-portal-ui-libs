== Question answered

How does a Remote Component add *its own* translation files to the page, at its own base URL, without re-implementing the loading, merging and page-wide sharing described in link:./app-translations.adoc[App translations load & sharing]?

== Why it exists

A Remote Component is a small, self-contained UI piece that one micro-frontend exposes and another host MFE or the Shell renders into a link:../remote-components/slot-rendering.adoc[Slot]. It is built and deployed as its own module-federation remote, so it ships its own `assets/i18n/` directory under its own base URL: a different origin and path from the host App's. A plain i18n setup that points at a single base path cannot pick those up.

The design therefore reuses the same mechanism every App already uses: the translation path is a *multi-value* token, and a Remote Component simply contributes *one more* entry for its own base URL. The loader chain, the deep merge and the global cache are shared with the host, so a file the Remote Component and the host both need is still fetched once. The Remote Component is not a special case in the loader: it is another participant that registers a path.

== How it works

The framework-agnostic rule is one sentence: **each source on the page contributes exactly one translation base path, and nothing downstream knows which source it came from.**

[source,mermaid]
----
flowchart TD
  subgraph "each source on the page"
    App["host App<br/>assets/i18n/"]
    Lib["shared lib<br/>onecx-angular-utils/assets/i18n/"]
    RC["Remote Component<br/>assets/i18n/ at its own baseUrl"]
  end
  App -->|one entry| T["TRANSLATION_PATH<br/>(multi token)"]
  Lib -->|one entry| T
  RC -->|one entry| T
  T --> O[OnecxTranslateLoader]
  O --> C[one CachingTranslateLoader per unique path]
  C --> Cache["window.onecxTranslations<br/>(shared with every App)"]
  C --> M["deep-merged table<br/>(mergeDeep)"]
----

The path each source contributes is *its own* base URL. For a host App and for a library that is the base URL the bundler can see at build time (`import.meta.url`), so it is captured at registration with link:{libs}/angular-utils/src/lib/providers/translation-path-from-meta.providers.ts[`provideTranslationPathFromMeta(import.meta.url, 'assets/i18n/')`], which strips the file name from `import.meta.url` and appends the segment. For a Remote Component the base URL is *not* available at build time; it is only known once the host has resolved the component's `remoteComponent.baseUrl` (the origin and mount path the Shell publishes on the link:{libs}/integration-interface/src/lib/topics/remote-components/v1/remote-component.model.ts[`RemoteComponent`]). The Remote Component therefore points the same provider at its *own* `import.meta.url`, which, because the component's code runs from its own federation remote, already resolves to a URL under that `baseUrl`. The result is one `TRANSLATION_PATH` entry at the component's own base URL, indistinguishable from any other entry by the time it reaches the loader.

Once the entries exist, everything is exactly as in link:./app-translations.adoc[App translations load & sharing]: link:{libs}/angular-utils/src/lib/utils/onecx-translate-loader.utils.ts[`OnecxTranslateLoader`] reads every `TRANSLATION_PATH` value, deduplicates them, builds one link:{libs}/angular-utils/src/lib/utils/caching-translate-loader.utils.ts[`CachingTranslateLoader`] per unique path, wraps them in link:{libs}/angular-utils/src/lib/utils/translate.combined.loader.ts[`TranslateCombinedLoader`], and the link:{libs}/angular-utils/src/lib/services/translation-cache.service.ts[`TranslationCacheService`] guarantees the same file is fetched once page-wide. That shared chain is documented there and is not repeated here; a Remote Component gains the *fetch once* guarantee for free because it shares the same `window.onecxTranslations` and the same combined loader.

The one thing that differs is *when and where the entry is created*. A host App registers it in its own module bootstrap. A Remote Component registers it at its own bootstrap, after the host has called it. Concretely, the host renders the component (link:{libs}/angular-remote-components/src/lib/components/slot/slot.component.ts[the `ocx-slot` rendering path]) and hands it a `RemoteComponentConfig`, carrying `appId`, `productName`, `permissions` and the `baseUrl` the host resolved, through `ocxInitRemoteComponent` (Angular) or the `ocxRemoteComponentConfig` property (web component). The component's own bootstrap then adds the `TRANSLATION_PATH` entry at its own base URL, and the page-wide loader picks it up alongside the host's entries.

== Libs side / Shell side

=== Libs side

The whole mechanism is a set of `@onecx/angular-utils` providers and loaders. The public entry point for *any* source, host App, library or Remote Component, is link:{libs}/angular-utils/src/lib/providers/translation-path-from-meta.providers.ts[`provideTranslationPathFromMeta`]; a Remote Component uses it exactly like a library (link:{libs}/angular-utils/src/lib/providers/translation-path.providers.ts[`provideTranslationPaths()`] for the `angular-utils` library itself is the same call with a different segment). The `baseUrl` the host passes to the component is modelled by link:{libs}/angular-utils/src/lib/model/remote-component-config.model.ts[`RemoteComponentConfig`] and delivered through link:{libs}/angular-remote-components/src/lib/components/slot/slot.component.ts[the slot rendering path]. The merge and cache are link:{libs}/angular-utils/src/lib/utils/deep-merge.utils.ts[`mergeDeep`] and link:{libs}/angular-utils/src/lib/services/translation-cache.service.ts[`TranslationCacheService`], shared with every other source.

There is a deprecated factory, link:{libs}/angular-utils/src/lib/utils/remote-component-translation-path-factory.utils.ts[`remoteComponentTranslationPathFactory(path)`], that existed before `provideTranslationPathFromMeta` made the base URL implicit. It returns an `Observable<string>` that maps a `ReplaySubject<RemoteComponentConfig>` to `config.baseUrl + path`, i.e. it derived the path from the host-supplied `baseUrl` at runtime instead of reading `import.meta.url`. It is marked `@deprecated` in favour of `provideTranslationPathFromMeta(import.meta.url, 'assets/i18n/')`; its sibling for host Apps is link:{libs}/angular-utils/src/lib/utils/translation-path-factory.utils.ts[`translationPathFactory(path)`]. New Remote Components should not use either.

=== Shell side

The Shell does not translate Remote Components itself. It owns the *input* the whole chain depends on: the `baseUrl` each `RemoteComponent` is served from, which the Slot renders (see link:../remote-components/slot-rendering.adoc[Slot rendering]). Because the component's code runs from that base URL, a `provideTranslationPathFromMeta(import.meta.url, ...)` inside the component already resolves to the right origin and the Shell does nothing further. The only place the Shell participates directly in loading translations is its own `app.module.ts` (it is itself an App, and loads the shared-library strings the same way every App does: see link:./app-translations.adoc[App translations load & sharing]).

== Angular / React

The loader chain and the shared cache are Angular-specific, so the *fetch once* guarantee a Remote Component inherits is an Angular one.

* **Angular**: the Remote Component is bootstrapped as a module (or via link:{libs}/angular-webcomponents/src/lib/utils/webcomponent-bootstrap.utils.ts[`bootstrapRemoteComponent()`] for a web component); its `providers` include `provideTranslationPathFromMeta(import.meta.url, 'assets/i18n/')`. The entry is picked up by the page's `OnecxTranslateLoader`.
* **React**: a Remote Component has no equivalent of `window.onecxTranslations`; it relies on i18next's per-instance resource handling and the browser's HTTP cache rather than the shared cache. Its translation path is built with `getTranslationPathFromMeta` in link:{libs}/react-utils/src/lib/utils/translationResources.ts[`translationResources.ts`], as described in link:./react-translations.adoc[React translations]. The "fetch once, page-wide" guarantee therefore applies to the Angular side of the page only.

== Edge cases & pitfalls

* **`import.meta.url` under `file://`**: `provideTranslationPathFromMeta` throws at runtime when `import.meta.url` is unavailable or a `file://` URL (in tests, `isTest()` falls back to the raw segment instead). A Remote Component must be served over HTTP and the bundler must expose `import.meta.url`; the webpack `importMeta` setting is the usual culprit when this fails.
* **Duplicate base URLs**: if the host and the Remote Component resolve to the same base URL, `OnecxTranslateLoader` deduplicates the `TRANSLATION_PATH` values with a `Set`, so the shared files are still loaded once.
* **Merge order matters**: the Remote Component's entries join the same `mergeDeep` fold as the host's, so a key defined in both is resolved by the *order* the `TRANSLATION_PATH` values were provided, not by "host wins" or "component wins". If a component and the host define the same key with different values, the later-provided path wins.
* **Component loads after the host's language is already active**: the entry is added at component bootstrap; because the loader resolves `TRANSLATION_PATH` lazily at load time and the cache is shared, files the host has already fetched are reused rather than re-fetched.
* **Deprecated factory in a component's providers**: `remoteComponentTranslationPathFactory` still works but reads the host-supplied `baseUrl` at runtime; if a component on it is hosted at a different `baseUrl` than the one it built its path for, its translations will 404. Migrate to `provideTranslationPathFromMeta`.

== Debugging

* `window.onecxTranslations` is inspectable from the console; a Remote Component's files appear under their own base-URL keys just like the host's, so you can confirm the component's path was registered by checking for keys under its `baseUrl`.
* The combined loader logs under `TranslateCombinedLoader` and the cache under `TranslationCacheService`; a failed component file is logged with the offending loader and error.
* Confirm the `baseUrl` the host actually passed: it is the value the slot rendering path hands to `ocxInitRemoteComponent` / `ocxRemoteComponentConfig` (link:{libs}/angular-remote-components/src/lib/components/slot/slot.component.ts[the slot component]).

== Known issues

There is no known issue in this Unit as of the current `main` code. The shared loader chain that the "fetch once" guarantee relies on has its own documented coordination rule in link:./app-translations.adoc[App translations load & sharing]; a Remote Component inherits that behaviour unchanged.
