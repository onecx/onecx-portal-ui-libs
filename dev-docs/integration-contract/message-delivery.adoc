Unit 2 of the link:README.adoc[Integration Contract & Topics] Area. Unit 1, link:why-message-based.adoc[Why a message-based contract], explains *why* units talk only through Topics. This Unit explains *how* a message reaches every subscriber in the right order.

== Question answered

How does a published Topic value reach every subscriber, including late ones, in the right order, and when is the publish confirmed?

== Why it exists

A `Topic` value is shared between units that are not loaded together. Delivery must handle three consequences:

* *Propagation.* The publisher and its subscribers are independent `Topic` instances. A new value must reach every instance; there is no shared field.
* *Late subscribers.* A subscriber created after the publish, for example an App `Topic` constructed after the Shell published the workspace, must still receive the current value.
* *Ordering and confirmation.* Messages arrive out of order and duplicated across transports. A subscriber must keep only the latest value, and a caller must be able to `await` a publish until the value is applied everywhere.

== How it works

=== Message types

Every message is a `TopicMessage`, which extends the base `Message` (link:{libs}/accelerator/src/lib/topic/message.ts[`message.ts`], link:{libs}/accelerator/src/lib/topic/topic-message.ts[`topic-message.ts`]). Each `Message` carries:

* a `timestamp` from `performance.now()`;
* an `id` from a page-wide, monotonically increasing counter (`globalThis.onecxMessageId++`).

`TopicMessageType` (link:{libs}/accelerator/src/lib/topic/topic-message-type.ts[`topic-message-type.ts`]) defines three types:

[cols="1,2,3", options="header"]
|===
|Type |Class |Purpose

|`TopicNext`
|`TopicDataMessage<T>` extends `TopicMessage` and adds `data: T` (link:{libs}/accelerator/src/lib/topic/topic-data-message.ts[`topic-data-message.ts`])
|Carries the payload. Sent on every publish.

|`TopicGet`
|`TopicMessage`
|Requests the current value. Sent by a new `Topic` at construction (see below). A `Topic` that has a value answers by re-sending its `TopicNext` (link:{libs}/accelerator/src/lib/topic/topic.ts[`handleTopicGetMessage`]).

|`TopicResolve`
|`TopicResolveMessage` extends `TopicMessage` and adds `resolveId`, the `id` of the `TopicNext` it confirms (link:{libs}/accelerator/src/lib/topic/topic-resolve-message.ts[`topic-resolve-message.ts`])
|Acknowledges a publish.
|===

=== publish and the resolve handshake

`TopicPublisher.publish(value)` (link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`]):

1. Builds a `TopicNext` (`TopicDataMessage`) for the value and sends it.
2. Builds a `TopicResolve` whose `resolveId` is that message's `id`, registers a resolver promise for that `id` in `publishPromiseResolver`, and sends it.
3. Returns the promise.

The `Topic` holding the resolver for that `resolveId` resolves it and stops the event's propagation (`handleTopicResolveMessage`, link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). The browser processes queued messages in order, so every `Topic` instance in the tab handles the `TopicNext` before the `TopicResolve`. `await topic.publish(value)` therefore returns only after every instance could apply the value. `Gatherer` awaits a publish this way before reading the gathered responses (link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`]).

[source,mermaid]
----
sequenceDiagram
  participant Publisher as Topic (publisher)
  participant Browser as Browser message queue
  participant Subscriber as Topic (subscriber)

  Publisher->>Browser: send TopicNext (id=1)
  Publisher->>Browser: send TopicResolve (resolveId=1)
  Note over Publisher: publish() awaits the returned promise
  Browser-->>Subscriber: TopicNext (id=1)
  Subscriber->>Subscriber: handleTopicNextMessage -> apply value
  Browser-->>Publisher: TopicResolve (resolveId=1)
  Publisher->>Publisher: handleTopicResolveMessage -> resolve promise
  Note over Publisher: publish() resolves only now
----

==== Worked example: three live instances

Within one message, instances run oldest-created first. Each `Topic` registers its `window` `message` listener once, in its constructor (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]), and the browser calls a target's listeners in the order they were added. Across messages, every instance finishes the `TopicNext` before the `TopicResolve` is dispatched.

Take three live instances of the same `name`/`version`: `T1` (created first), `T2` (created second) and `P` (created third, about to publish). One `P.publish(value)` call runs like this:

1. `P` builds the `TopicNext` (`id=1`) and sends it (`postMessage`/`BroadcastChannel`).
2. `P` builds the `TopicResolve` (`resolveId=1`), stores a resolver for `id=1` in its `publishPromiseResolver`, sends it and returns a pending promise.
3. The browser delivers the `TopicNext` to every listener in creation order:
.. `T1.handleTopicNextMessage` applies the value (it beats `T1`'s stored id/timestamp).
.. `T2.handleTopicNextMessage` applies the value.
.. `P.handleTopicNextMessage` applies the value, because `P` is a subscribing instance too.
4. Only then does the browser deliver the `TopicResolve`, in the same order:
.. `T1.handleTopicResolveMessage` finds no resolver for `resolveId=1` (it published nothing) and does nothing.
.. `T2.handleTopicResolveMessage` does the same.
.. `P.handleTopicResolveMessage` finds its resolver, resolves it and calls `stopImmediatePropagation` (link:{libs}/accelerator/src/lib/topic/topic.ts[`handleTopicResolveMessage`]).
5. Only now does `await P.publish(value)` return.

=== Ordering by id and timestamp

A subscriber keeps exactly one value, in a `BehaviorSubject` called `data`. For each incoming `TopicNext`, `handleTopicNextMessage` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]) accepts the message only when one of these holds:

* The subscriber has no value yet. The first value always wins, regardless of order.
* The subscriber is initialised, both messages have an `id`, and the incoming `id` is greater than the stored one.
* The subscriber is initialised and the incoming `timestamp` is greater than the stored one.

Accepting sets `isInit` to `true` and resolves the `isInitialized` promise. Any other message is dropped, so a late or out-of-order `TopicNext` never overwrites a newer value.

A `Topic` answers a `TopicGet` only when it is initialised *and* holds a value (`onWindowMessage` / `onBroadcastChannelMessageV2`, link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). A `Topic` still waiting for its first value stays silent.

=== init and the first `TopicGet`

With `sendGetMessage = true` (the default), the `Topic` constructor broadcasts a `TopicGet` so that a running instance replays its value (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`], constructor). If the Shell has just started (`topic.initDate` less than 2 seconds ago), the request waits 100 ms so other Topics can initialise first, and is skipped if the `Topic` received a value meanwhile.

With `sendGetMessage = false`, the `Topic` does not ask for state at start-up. Request/response (RPC) Topics and the `Gatherer`'s internal topic use this to avoid an unwanted replay (link:why-message-based.adoc[Unit 1], link:gatherers-and-rpc-topics.adoc[Gatherers & RPC Topics]).

`Topic.isInitialized` resolves as soon as the first value is applied, and `asObservable()` emits nothing until `isInit` is set (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). Consumers use these to know when a value is safe to read.

== Libs side / Shell side

=== Libs side

The accelerator holds the whole framework-agnostic mechanism: message classes, ordering, replay and the resolve handshake (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`], link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`], link:{libs}/accelerator/src/lib/topic/message.ts[`message.ts`], the three message type files, link:{libs}/accelerator/src/lib/declarations.ts[`declarations.ts`]). The `@onecx/integration-interface` Topics are thin subclasses that override none of it. They only fix `name` and `version`, and RPC Topics also set `sendGetMessage = false`.

=== Shell side

The Shell is the primary *first* publisher. It constructs the shared Topics and publishes the initial state (workspace, theme, user profile, …) that later `TopicGet` requests replay. An App that starts after the Shell therefore still receives it. The Shell also answers RPC Topics (link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`], `ParametersTopic` publishing in link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`]).

== Angular / React

Delivery is the same in both: each adapter uses the framework-agnostic `Topic`. They differ only in how they wait for the first value:

* *Angular* services expose the topic's `isInitialized` promise and read values with `firstValueFrom(topic.asObservable())` (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]).
* *React* contexts subscribe the topic to React state and expose `isInitialized: config$.isInitialized` in the context value (link:{libs}/react-integration-interface/src/lib/contexts/configurationContext.tsx[`configurationContext.tsx`]).

In both, the `asObservable()`/`isInit` filter prevents rendering an undelivered value.

== Edge cases & pitfalls

* *No read-after-write on the publisher.* Synchronous `getValue`-style reads and the `isInitialized` promise describe the *delivered* value, not the value other instances will apply. `SyncableTopic` (link:{libs}/accelerator/src/lib/topic/syncable-topic.ts[`syncable-topic.ts`]) exposes exactly this and is `@deprecated` for that reason.
* *Equal timestamps.* If two messages share a `timestamp` and only one has an `id` (the other is an "old style" message), the subscriber drops the incoming one. It logs a warning to upgrade all libraries to the latest version (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). This is a migration aid, not normal operation.
* *Several transports.* A `Topic` listens on the page message channel and, when enabled, on the BroadcastChannel v1 and v2 channels (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). Channel choice and fallback are covered in link:transports-and-tab-scope.adoc[Transports & tab scope].
* *Replay is best-effort.* Replay needs another initialised instance of the same topic that holds a value. The first instance waits for the first real `TopicNext`.

== Debugging

The accelerator logs each received message and each accept/drop decision under the topic's own namespace (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). For the `localStorage.debug` patterns, see the Area's link:README.adoc#debugging-conventions[Debugging conventions].

== Known issues

None in the delivery core on current `main`. The deprecated `SyncableTopic` (see Edge cases) exposes the delivery model in an easily misused way; its JSDoc marks it deprecated (link:{libs}/accelerator/src/lib/topic/syncable-topic.ts[`syncable-topic.ts`]).
