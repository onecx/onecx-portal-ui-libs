Unit 3 of the link:README.adoc[Integration Contract & Topics] Area. Unit 2 (link:message-delivery.adoc[Topic message delivery]) covers *what* a Topic message is and *how* it reaches subscribers. This Unit covers *where* it travels and *why* normal traffic stays inside one tab.

== Question answered

How does the accelerator pick the browser channel for a Topic's messages: tab-scoped BroadcastChannel v2 (keyed by a tab id), broad v1, or `window.postMessage`?

== Why it exists

One OneCX tab hosts the Shell, the routed App and any Remote Components (link:why-message-based.adoc[Unit 1]). They must sync with each other, but not necessarily with other tabs. Two constraints follow:

* *Same tab, many independent units.* The units are separate bundles sharing one `window`. Their channel must reach every unit in the tab without leaking into other tabs of the site. A Shell and App open in two tabs are independent instances and share no state by default.
* *Compatibility.* A unit built against an older library may know only one broad BroadcastChannel, or only `window.postMessage`. A new (v2) instance must still talk to it.

So the default channel is tab-scoped, and the shared send transport switches when messages arrive on legacy channels.

== How it works

=== The three transports

A shared state flag, `useBroadcastChannel`, selects one of three send channels (link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`sendMessage`]):

[cols="1,1,2", options="header"]
|===
|`useBroadcastChannel` |Transport |Channel name (per Topic)

|`'V2'` (default)
|BroadcastChannel, tab-scoped
|`TopicV2-<name>\|<version>-<tabId>`

|`true`
|BroadcastChannel, broad (legacy v1)
|`Topic-<name>\|<version>`

|`false`
|`window.postMessage`
|the page's `message` event (no dedicated channel)
|===

A `BroadcastChannel` connects only listeners with the same name. The v2 name ends in the `tabId`, so it stays inside one tab. The v1 name has no `tabId`, so it crosses tabs; that is why v1 is legacy, not the default.

=== Why the channel name encodes the Topic (context)

Encoding `name|version` in the channel name lets the browser filter traffic before any JavaScript runs. Unlike the rest of this Unit, this rationale is provided as team context and is not traced to a commit or diff.

* *Before:* an earlier accelerator used one channel for all Topics. Every `Topic` instance deserialized every message and checked `name`/`version` in JavaScript before dropping it, which scaled badly with many Topics and instances.
* *Now (v2):* the name includes `name|version` and `tabId`, so the browser never wakes an instance of a different Topic. The broad v1 channel survives only for peers that have not upgraded.

=== Shared state and fallback scenarios

All units in a tab share one state object, `globalThis['@onecx/accelerator'].topic`. The first library to load sets its defaults lazily:

* `useBroadcastChannel`: `'V2'`.
* `tabId`: `Math.ceil(performance.now())`.
* `initDate`: `Date.now()`.

Only the accelerator changes `useBroadcastChannel`, demoting it as messages arrive, so arrival order matters. A v2 message leaves the flag unchanged.

*Example 1: Mixed library generations.* App A (current, v2), App B (legacy v1-only) and App C (`postMessage`-only) share a tab:

. A sends on the tab-scoped v2 channel (`'V2'`).
. B sends on v1. The flag drops to `true`, so all later sends, including A's, use v1.
. C sends via `window.postMessage`. The flag drops to `false`, so later sends use `postMessage`.
. Read channels stay open, so a later v1 or window message flips the flag again (a v1 message sets it back to `true`).

*Example 2: No `BroadcastChannel` in the browser.* The first `Topic` constructed sets `useBroadcastChannel = false` before any channel opens, so every later `Topic` sends via `window.postMessage`. The publisher also checks for `BroadcastChannel` before each send and falls back to `postMessage`.

Delivery stays correct across channels because a subscriber accepts only the latest value by id/timestamp (link:message-delivery.adoc[Unit 2]).

=== Selecting the channel to send on

`TopicPublisher.sendMessage` builds the publish channels lazily (`createBroadcastChannel`) and then picks the send path (link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`]):

* `useBroadcastChannel === 'V2'` → post on the v2 (tab-scoped) publish channel.
* `useBroadcastChannel` is truthy (`true`) → post on the broad v1 publish channel.
* otherwise → `window.postMessage(message, '*')`.

Receiving uses every channel the constructor opened (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]): always a `window` `message` listener and, if `useBroadcastChannel` is truthy, both a v1 and a v2 *read* channel. The v1 read channel opens even in v2 mode so the page can detect a legacy peer and demote.

== Libs side / Shell side

=== Libs side

The whole mechanism lives in the framework-agnostic `@onecx/accelerator`:

* link:{libs}/accelerator/src/lib/declarations.ts[`declarations.ts`] holds the shared state and its defaults.
* link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`] and link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`] hold the channel names, the send selection and the demotion handlers.

No App code or configuration chooses the transport; the `tabId`, the default `'V2'` and the fallbacks are internal.

=== Shell side

The Shell does not select the transport. Before bootstrapping the module, it advertises which *Topics* it provides (for example `PARAMETERS_TOPIC`, `CURRENT_LOCATION_TOPIC`) via `ShellCapabilityService.setCapabilities(…)` (link:{shell}/src/bootstrap.ts[`bootstrap.ts`]). That is the Unit 6 capability list, not a transport choice.

At runtime the Shell is just more `Topic` instances in the tab, with the same tab scoping and fallback as an App's. It publishes shared state and answers its RPC Topics (for example link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`] and link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`]).

== Angular / React

There are no framework differences: Angular services and React contexts wrap the same `Topic` (link:framework-adapters.adoc[Framework adapters]). Neither the Angular adapter (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]) nor the React adapter (link:{libs}/react-integration-interface/src/lib/contexts/configurationContext.tsx[`configurationContext.tsx`]) touches `useBroadcastChannel`, the `tabId` or the channels.

== Edge cases & pitfalls

* *Tab scoping is a heuristic.* `tabId` is `Math.ceil(performance.now())` at first accelerator load, not a server-assigned id. Two tabs normally differ, but the value is not globally unique. Do not use it as an identity.
* *v1 is not the default cross-tab contract.* The broad v1 channel (`Topic-…`) has the same name in every tab and is used only as a fallback after a legacy peer is detected. Do not treat it as the normal cross-tab bridge (link:why-message-based.adoc[Unit 1]).
* *A transport change affects sends for the whole tab.* `useBroadcastChannel` is shared, so a message received by one Topic switches all later sends in the tab until the flag changes again.
* *Receivers keep listening on all opened channels.* Only `destroy` closes the v1/v2 read channels, so a Topic demoted to `postMessage` still listens on them. This is harmless (id/timestamp filtering drops stale messages), but the read side never shrinks.
* *Mixed environments.* A message from a `postMessage`-only unit sets the send flag to `false`, and a later v1 BroadcastChannel message can set it back to `true`. Do not assume the transport stays on `postMessage` after the first window message.

== Debugging

Observe the transport at two levels (general `localStorage.debug` patterns: link:README.adoc#debugging-conventions[Debugging conventions]):

* *Which channel a message used.* Each `Topic` logs at its `@onecx/accelerator:Topic:<name>` namespace whether a message arrived "via window" or via a BroadcastChannel (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). The demotion handlers log at `info` when they switch the shared flag.
* *The current transport for the tab.* In the console, inspect `globalThis['@onecx/accelerator'].topic.useBroadcastChannel` (`'V2'` / `true` / `false`) and `.tabId`. A value of `false` means the tab has fallen back to `postMessage`.

== Known issues

* *Read channels are not closed on demotion.* `disableBroadcastChannel`/`disableBroadcastChannelV2` only flip the send flag. The v1/v2 read channels opened in the constructor stay open until `destroy` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). This is intended, since delivery is de-duplicated by id/timestamp, but easy to misread as a resource leak. See link:topic-lifecycle.adoc[Topic lifecycle] for what `destroy` releases.
