This is Unit 4 of the link:README.adoc[Integration Contract & Topics] Area. Units 2 and 3 (link:message-delivery.adoc[Topic message delivery], link:transports-and-tab-scope.adoc[Transports & tab scope]) explain how and where a message travels. This Unit covers the *lifecycle* of a Topic: creation, publishing, destruction, and what a destroyed Topic still holds.

== Question answered

What is the lifecycle of a Topic: what creation and `destroy` acquire and release, where the Angular and React adapters destroy Topic/Gatherer instances, and where leaks or double-destroy can come from?

== Why it exists

A `Topic` is a *subscription*, not a value. Its constructor registers a `window` `message` listener and opens one or two `BroadcastChannel` handles, and the instance holds them until it is destroyed (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]).

The owners of `Topic` instances (App routes, Remote Components, React components) load and unload constantly. If a destroyed owner keeps its Topics alive, each unload leaks idle `window` listeners and open `BroadcastChannel`s, and those Topics keep reacting to traffic.

The cost is also performance. Every message on a channel reaches *every* attached listener and runs `handleTopicNextMessage`/`handleTopicGetMessage` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]), even for instances nobody reads. If a repeatedly visited route never destroys its `Topic`, live listeners grow across the session, and each publish costs one callback per surviving instance. Destroying a `Topic` with its owner keeps that cost bounded to the instances in use.

== How it works

=== Creation

Constructing a `Topic` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]):

* Registers a `window` `message` listener (`onWindowMessage`).
* If the transport is enabled, opens the v1 and v2 `BroadcastChannel` *read* handles. The v1/v2 *publish* handles are created lazily on the first `sendMessage` via `createBroadcastChannel` (link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`]).
* Sends an initial `TopicGet` so the current value is replayed, unless built with `sendGetMessage = false` (see link:message-delivery.adoc[Unit 2]).
* With stats enabled, increments the per-topic *instances created* counter on `globalThis` (`increaseInstanceCount`, link:{libs}/accelerator/src/lib/utils/logs.utils.ts[`logs.utils.ts`]).

The Topic is alive from construction and owns these resources until `destroy` is called.

=== Publishing

`Topic` extends `TopicPublisher`, which provides publishing (link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`]). `publish(value)` sends a `TopicNext` and a `TopicResolve` message. It returns a promise that resolves once the value is applied (resolve handshake: link:message-delivery.adoc[Unit 2]). There are two publishing shapes:

* *A `Topic` as its own publisher.* Most shared Topics publish this way, for example `configuration.service.ts` calls `config$.publish(…)`.
* *A standalone publisher.* A class extends `TopicPublisher` and publishes without keeping a `Topic` alive for reads. For example, `ResizedEventsPublisher` publishes the `resizedEvents` topic, while consumers subscribe to a separate `ResizedEventsTopic` built with `sendGetMessage = false` (link:{libs}/integration-interface/src/lib/topics/resized-events/v1/resized-events.topic.ts[`resized-events.topic.ts`]). A standalone publisher owns no listeners, only lazily created publish channels, so it has no `destroy`.

RPC Topics and `Gatherer` build request/response on the same `publish` (link:gatherers-and-rpc-topics.adoc[Request/response: Gatherers & RPC Topics]). The Shell answers an RPC Topic by publishing onto it (link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`]).

=== Destroy and cleanup

`Topic.destroy()` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`], `destroy`):

* Tries to remove the `window` `message` listener, but a capture-flag mismatch leaves it attached (see <<known-issues>>).
* Closes the v1 and v2 *read* `BroadcastChannel` handles.
* Closes the v1 and v2 *publish* `BroadcastChannel` handles.

`Gatherer.destroy()` also unsubscribes its internal topic subscription, calls `topic.destroy()`, and deletes its pending request ids from the shared `acceleratorState.gatherer.promises` map (link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`]).

`destroy` does *not* clear `publishPromiseResolver`, complete the internal `data` `BehaviorSubject`, unsubscribe external subscribers, or reset `isInit`. The channels close, but the leaked `window` listener can still deliver messages to the Topic.

=== Where destroy is called

* *Angular:* the owning service destroys its `Topic` in `ngOnDestroy`.
* *React:* `useTopic` destroys the `Topic` it created on unmount, but not an external instance.
* *Shell:* as the long-lived tab host, it publishes initial state and answers RPCs for the whole tab. Its services are root-provided and created once per tab, so any `destroy` they run fires when the tab closes, not on navigation. Some never destroy their Topics at all (for example link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`]); others, such as link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`], call `destroy` in `ngOnDestroy`.

<<angular-react>> gives the framework details; link:framework-adapters.adoc[Framework adapters] covers the adapters as a whole.

=== Deprecated: SyncableTopic

`SyncableTopic` (link:{libs}/accelerator/src/lib/topic/syncable-topic.ts[`syncable-topic.ts`]) is a `@deprecated` `Topic` subclass that exposes the value synchronously via `getValue()`, with no read-after-write guarantee. Its lifecycle and `destroy` are the same as `Topic`. Reading asynchronous shared state synchronously is unsafe, so use a regular `Topic` and `await isInitialized` instead.

== Libs side / Shell side

=== Libs side

`@onecx/accelerator` provides the lifecycle primitives:

* `Topic`/`TopicPublisher` (`destroy`, the read/publish channels, the resolve map) in link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`] and link:{libs}/accelerator/src/lib/topic/topic-publisher.ts[`topic-publisher.ts`].
* `Gatherer.destroy` in link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`].

The framework adapters *call* `destroy` at the right lifecycle point: the Angular `OnDestroy` hook (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]) and the React `useTopic` cleanup (link:{libs}/react-integration-interface/src/lib/utils/use-topic.utils.ts[`use-topic.utils.ts`]).

=== Shell side

The Shell holds its shared Topics for the tab's lifetime and answers its RPC Topics by publishing (link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`], link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`]). It is the only long-lived Topic holder, so per-route cleanup falls to Apps and Remote Components through the adapters.

== Angular / React

Only the destroy *point* differs. Both trigger the same `Topic.destroy`.

* *Angular:* a service implements `OnDestroy` and destroys its `Topic` in `ngOnDestroy`. For example, `ConfigurationService` holds one lazily created `ConfigurationTopic` and destroys it on teardown (link:{libs}/angular-integration-interface/src/lib/services/configuration.service.ts[`configuration.service.ts`]).
* *React:* `useTopic` creates a `Topic` lazily, only when no external instance is passed. On unmount it defers `destroy` with a zero-delay `setTimeout`, guarded by a mounted ref, so a StrictMode double-mount does not destroy a topic the component immediately reuses (link:{libs}/react-integration-interface/src/lib/utils/use-topic.utils.ts[`use-topic.utils.ts`]). The hook never destroys an *external* instance; ownership stays with the caller.

== Edge cases & pitfalls

* *Calling `destroy` twice is safe.* The `BroadcastChannel` handles are optional-chained, and `removeEventListener` and closing an already-closed channel are no-ops, so double-destroy does not throw.
* *The `useTopic` hook does not clean up external React topics.* The caller must destroy a `Topic` it passes in. Forgetting this on route change leaks the topic.
* *Destroy does not stop in-flight `publish` promises.* `destroy` does not clear `publishPromiseResolver`, so a pending publish still resolves when its `TopicResolve` message is processed.
* *Destroy does not complete external subscriptions.* `asObservable()` subscriptions stay active, and the leaked `window` listener may still deliver messages. Consumers must unsubscribe themselves.
* *Leak watch-point.* The `window` message listener is the only real leak in the current code (see <<known-issues>>). `destroy` releases all four `BroadcastChannel` handles.

== Debugging

* *Count instances.* With stats enabled, `globalThis['@onecx/accelerator'].topic.stats.instancesCreated` shows the `Topic` instances created per topic name (link:{libs}/accelerator/src/lib/utils/logs.utils.ts[`logs.utils.ts`]). A growing count for a topic that should be a singleton per tab is the first sign of a leak.
* *Watch the lifecycle logs.* `Topic` and `TopicPublisher` log at `@onecx/accelerator:Topic:<name>` / `:TopicPublisher:<name>`. `Gatherer` logs at `@onecx/accelerator:Gatherer:<name>`, including its `created`/`destroyed` milestones. For `localStorage.debug` patterns, see the Area's link:README.adoc#debugging-conventions[Debugging conventions].

== Known issues

* *`destroy` does not actually remove the `window` message listener.* The constructor registers the listener with default options (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`], constructor), but `destroy` calls `removeEventListener('message', this.windowEventListener, true)`. Per the DOM spec, removal must use the same capture value as registration (`false`), so the call with `true` removes nothing. A destroyed `Topic` therefore keeps a live listener that can still call `handleTopicNextMessage` and apply values. The repository's spec (link:{libs}/accelerator/src/lib/topic/topic.spec.ts[`topic.spec.ts`]) pins the `true` argument, recording the current behaviour rather than flagging a bug. _Follow-up:_ call `removeEventListener` without a capture argument, matching the constructor, so `destroy` detaches the listener.
