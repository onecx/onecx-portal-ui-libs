Unit 8 of the link:README.adoc[Integration Contract & Topics] Area is its reference table: every shared `Topic` and `Gatherer` the libraries define. Units 1–7 explain the contract these entries build on.

== Question answered

Which shared `Topic`s and `Gatherer`s do the OneCX libraries define, and what is each one's version, publisher, consumers and owning Area?

== Why it exists

Units 1–6 describe the general messaging contract, but every other Area builds on the concrete channels. One list of all `Topic` and `Gatherer` implementations, pinned to `main`, shows *which* Topics exist, at which version, and *where* each one is explained (its owning Area). It also makes the contract auditable: a new Topic or a version bump shows up here as a row.

This page does not re-explain entries. Units 1–4 cover the Topic *mechanism*; the owning Area covers each Topic's *meaning*.

== How it works

A `Topic` is a `name`/`version` pair that subclasses the framework-agnostic base `Topic` (link:{libs}/accelerator/src/lib/topic/topic.ts[`topic.ts`]). Request/response Topics also set `sendGetMessage = false`. A `Gatherer` is a `name`/`version` pair that subclasses the base `Gatherer` (link:{libs}/accelerator/src/lib/utils/gatherer.ts[`gatherer.ts`]). Each concrete entry in `@onecx/integration-interface` is a thin subclass that only fixes the name, the version and, for RPC Topics, the flag. The tables below come from those subclass definitions on `main`.

Three columns need a definition:

* *Publisher:* who normally publishes the value. That is the Shell for shared state and the App/Remote Component for Topics an App publishes at bootstrap. RPC Topics name both the *ask* side and the *answer* side.
* *Consumers:* the framework adapters that wrap the Topic so App code can read it and, where relevant, write it. See link:framework-adapters.adoc[Framework adapters].
* *Owning Area:* the Dev Docs Area that explains the Topic's *meaning*. Links use the planned slugs in the link:{dev-docs-index}[index]; some target pages are not written yet.

== Libs side / Shell side

=== Libs side

`@onecx/integration-interface` defines the entries: `Topic` subclasses under `src/lib/topics/` and `Gatherer` subclasses under `src/lib/gatherers/`, all exported from the package barrel (link:{libs}/integration-interface/src/index.ts[`index.ts`]). Two entries live elsewhere: `TranslationCacheTopic` in `@onecx/angular-utils`, and the guards' `GuardGatherer` in `@onecx/angular-utils/guards` and `@onecx/react-utils`.

=== Shell side

The Shell *publishes* most shared-state Topics, including parameters (link:{shell}/src/app/shell/services/parameters.service.ts[`parameters.service.ts`]). It *answers* the `PermissionsRpcTopic` it owns (link:{shell}/src/app/shell/services/permission-proxy.service.ts[`permission-proxy.service.ts`]). It advertises which Topics it provides through the capability list (link:versioning-and-capabilities.adoc[Unit 6]).

== Angular / React

Only the *Consumers* column differs per framework. The Angular adapter is an `@Injectable` service and the React adapter a context/hook; both wrap the same `Topic` (link:framework-adapters.adoc[Unit 7]). Both frameworks share the framework-agnostic `IconService`, `NotificationService`, `ImageRepositoryService` and `DynamicTranslationService`.

== Edge cases & pitfalls

* *The table is a snapshot of `main`.* `Topics` are versioned per directory: a new `v2/` folder adds a row, and a version bump changes the `Version` column. If this page and the code disagree, the code wins.
* *`name` and class name can differ.* `CurrentWorkspaceTopic` publishes under the name `currentPortal`, and `RemoteComponentsTopic` under `remoteComponentsInfo`. The transport channel is keyed on `name`|`version`, not on the class name (link:transports-and-tab-scope.adoc[Unit 3]).
* *`sendGetMessage = false` is not "RPC only."* `IconTopic`, `EventsTopic` and `ResizedEventsTopic` suppress the initial `TopicGet` for other reasons (Unit 2). Not every Topic with this flag is a true request/response channel.
* *Two classes per resized Topic.* `ResizedEventsTopic` (the read side) and `ResizedEventsPublisher` (the publish side, a `TopicPublisher` in link:{libs}/integration-interface/src/lib/topics/resized-events/v1/resized-events.topic.ts[`resized-events.topic.ts`]) are separate classes that share the name/version. They form one catalogue entry.

== Debugging

To watch a Topic or Gatherer, enable its namespace as described in the Area's link:README.adoc#debugging-conventions[Debugging conventions]. Take the `name` from the linked definition; for example, `CurrentWorkspaceTopic` declares `currentPortal`.

== Known issues

* *`TranslationCacheTopic` runs ahead of the rest at version 2.* Every other Topic here is at version `1`, so `TranslationCacheTopic` is the live example of a version bump (link:versioning-and-capabilities.adoc[Unit 6]).
