Integration Contract & Topics

Area 1 of the OneCX Dev Docs

A walkthrough of how Apps, Remote Components and the Shell talk to each other.

Problem

A OneCX page hosts several independently built, independently released units at once — one Shell, the routed App, and any Remote Components it hosts — in different frameworks, with no shared object graph and no guarantee they load together.

Yet they must stay in sync: the Shell owns the workspace, theme, route and user profile — and Apps/Remote Components need to read and react to those values.

Big picture

  • Libraries (@onecx/accelerator, @onecx/integration-interface, Angular/React adapters) provide the Topic/Gatherer primitives.
  • Shell advertises capabilities, publishes shared state, answers requests.
  • Apps / Remote Components subscribe to state, may publish or answer too.

1Why a message-based contract

Units are built, versioned and released independently, run in different frameworks, and may load at different times — so no unit may ever hold a reference to another unit's code.

A unit can only (1) publish a message onto a Topic and (2) subscribe to a Topic. The only way to obtain a value from the Shell, or from another App, is to ask for it over a Topic and wait for the message that carries the answer.

Request/response is built from the same primitive: the asker publishes onto a Topic configured not to request state on start-up (sendGetMessage = false); the answerer subscribes and publishes the answer back.

2Topic message delivery

Every message carries a name and a version; a subscriber only accepts one where both match. publish(value) sends a TopicNext then a TopicResolve, and only resolves once every live instance has applied the value.

3Transports & tab scope

  • window.postMessage — broadcasts to everyone listening on the page's message event, no channel/filtering at all.
  • BroadcastChannel — delivers only to listeners that opened the same channel name; the browser itself filters before any JS runs.
useBroadcastChannelTransportChannel name (per Topic)

Per context given by the team running this audit: an earlier version used a single, shared channel for every Topic — every instance received every message and filtered it in JavaScript, which scaled badly as the number of Topics/instances grew. Folding name|version|tabId into the channel name moves that filtering down to the browser itself.

4Topic lifecycle

A Topic is a subscription, not a value: it registers a window listener and opens channels at construction, and holds them until destroy().

Every message is delivered to every listener still attached. If a route's Topic is never destroyed, live listeners for it only grow across the session — each later publish does proportionally more work, one callback per surviving instance.

5Gatherers & RPC Topics

Two request/response shapes built on the same Topic primitive.

Gatherer (scatter/gather)

One asker, every instance answers; the asker collects them all.

sequenceDiagram participant Caller participant Local as Gatherer (local) participant Remote as Gatherer (remote) Caller->>Local: gather(request) Local->>Local: id = Gatherer.id++, promises[id] = [] Local->>Remote: publish({ id, request }) Note over Caller: await publish (waits for all peers to register) Local->>Local: ownIds has id -> skip Remote->>Remote: not own -> promises[id].push(P) Remote->>Remote: callback(request) -> response Remote->>Remote: resolve(response) Note over Caller: publish resolved Caller->>Caller: Promise.all(promises[id]) -> Response[]

E.g. guards across Apps, or AI completion where you don't know who will answer.

5Gatherers & RPC Topics

RPC Topic (one asker, one designated answerer)

A plain Topic subclass with sendGetMessage = false — no replay, no promise array. The asker subscribes to the matching answer before publishing the request; the designated answerer republishes the answer onto the same topic, resolving the asker's subscription.

  • Ask — e.g. a Remote Component's PermissionService.getPermissions awaits a filtered subscription, then publishes { appId, productName } on the PermissionsRpcTopic.
  • Answer — the Shell's permission-proxy.service.ts filters for unanswered requests and republishes { appId, productName, permissions }.

No built-in timeout: if the designated answerer never responds, the asker's promise never resolves on its own.

6Versioning & Shell capability negotiation

Topic version

"Will this message be delivered at all?" — gates message acceptance per Topic.

Shell capability

"Does this Shell provide the feature I want?" — a per-Shell-run declaration, checked via hasShellCapability(cap).

  • CURRENT_LOCATION_TOPIC · PARAMETERS_TOPIC
  • ACTIVENESS_AWARE_MENUS · DYNAMIC_TRANSLATIONS_TOPIC

7Framework adapters

Angular wraps each shared Topic in an @Injectable service and destroys it in ngOnDestroy; React's useTopic hook creates it lazily and destroys only the instance it created, deferred past a StrictMode double-mount.

A further ngrx layer subscribes the shared Topic and dispatches store actions — covered in depth in Area 12 (Shell context → App ngrx store).
