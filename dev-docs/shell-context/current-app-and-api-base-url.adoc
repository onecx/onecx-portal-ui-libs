== Question answered

How does the Shell describe the *current* App (the product the page is currently showing), and how does an App resolve the base URL its backend API calls should be sent to?

== Why it exists

Many products (Apps) share one page in a Workspace; the *current* one is the one the user is looking at. An App does not know its identity (`appId`, `productName`) or base URL at build time, so the Shell must supply them:

* Some libraries (parameters, permissions, translations) resolve values per `appId` / `productName` and need to know *which* App is current.
* Generated API clients need the *base URL* of that App's backend so a call to `…/api/…` lands on the right host.

The `currentMfe` context carries the current App's identity and base URL; the libs resolve the API base URL from it instead of hard-coding one. "MFE" is the Module-Federation remote the App was loaded from. The Shell republishes the context whenever the current product changes.

== How it works

The context is published on the link:{libs}/integration-interface/src/lib/topics/current-mfe/v1/current-mfe.topic.ts[`current-mfe` Topic] (raw name `currentMfe`, version 1). Its value is the link:{libs}/integration-interface/src/lib/topics/current-mfe/v1/mfe-info.model.ts[`MfeInfo`] model:

* `appId`, `productName`: which product is current (used to key per-app lookups).
* `remoteBaseUrl`: the current App's base URL. **The API base URL is resolved from this value.**
* `baseHref`, `mountPath`: the (joined) base path the App is mounted at.
* `shellName` (always `portal`), `version`, `displayName`, `remoteName`, `elementName`, `remote`.

link:{libs}/angular-utils/src/lib/utils/portal-api-configuration.utils.ts[`PortalApiConfiguration`] resolves the API base URL. It supplies the configuration surface a generated OpenAPI client expects (`basePath`, `selectHeaderContentType`, `selectHeaderAccept`, `isJsonMime`, `lookupCredential`, `encodeParam`). On construction it seeds a `BehaviorSubject` with the placeholder `./<apiPrefix>`. It then maps the *first* `currentMfe$` value to `Location.joinWithSlash(currentMfe.remoteBaseUrl, apiPrefix)`:

[source,mermaid]
----
sequenceDiagram
  participant Gen as Generated client
  participant Cfg as PortalApiConfiguration
  participant MFE as currentMfe$ (from Shell)
  Gen->>Cfg: new (generatorConfig, apiPrefix)
  Note over Cfg: basePath = ./<apiPrefix> (placeholder)
  Cfg->>MFE: currentMfe$.pipe(first())
  MFE-->>Cfg: MfeInfo (remoteBaseUrl = app base URL)
  Cfg-->>Cfg: basePath = joinWithSlash(remoteBaseUrl, apiPrefix)
  Gen->>Cfg: basePath  (now the real host)
----

The `Topic` emits only after the Shell publishes a value (Unit 1), so `basePath` stays the placeholder until then. The `basePath` setter throws `Error('Do not set basePath')`, so a generated client cannot override the resolved value.

== Libs side / Shell side

=== Libs side

* link:{libs}/integration-interface/src/lib/topics/current-mfe/v1/mfe-info.model.ts[`MfeInfo`] / link:{libs}/integration-interface/src/lib/topics/current-mfe/v1/current-mfe.topic.ts[`CurrentMfeTopic`]: the model and Topic in `integration-interface`.
* link:{libs}/angular-integration-interface/src/lib/services/app-state.service.ts[`AppStateService.currentMfe$`]: the Angular accessor: a getter that lazily creates the `CurrentMfeTopic` and destroys it in `ngOnDestroy`. React mirrors it with link:{libs}/react-integration-interface/src/lib/contexts/appStateContext.tsx[`AppStateProvider`] / `useAppState().currentMfe$` (created via `useTopic`).
* link:{libs}/angular-utils/src/lib/utils/portal-api-configuration.utils.ts[`PortalApiConfiguration`]: the Angular API-base-URL resolver, exported from `@onecx/angular-utils`. The deprecated link:{libs}/angular-utils/src/lib/utils/translation-path-factory.utils.ts[`translationPathFactory`] uses the same pattern: it combines `currentMfe$` and `globalLoading$` to build the translation asset path from `remoteBaseUrl`.

=== Shell side

The Shell produces the context and *republishes* it per navigation, not once at bootstrap.

* *Per-App publish:* `RoutesService.updateMfeInfo` in link:{shell}/src/app/shell/services/routes.service.ts[`routes.service.ts`] builds `MfeInfo` from the current BFF route and calls `currentMfe$.publish(mfeInfo)`. `remoteBaseUrl` is the route's `url`; `baseHref` and `mountPath` are the route's (joined) `baseUrl`; `shellName` is `portal`. It runs from `updateAppEnvironment` → `updateAppState`, the `canActivateChild` guard on each converted route. The context therefore refreshes whenever the *current route's base URL changes*, so `remoteBaseUrl` always reflects the route the user is on. A guard skips the republish when `currentMfe.remoteBaseUrl` already equals the incoming route's URL.
* *Empty publish on not-found:* `PageNotFoundComponent` (link:{shell}/src/app/not-found/components/not-found-page/not-found-page.component.ts[`not-found-page.component.ts`]) publishes a *blank* `MfeInfo` in its constructor (`appId`, `productName`, `remoteBaseUrl` all empty strings, `baseHref: '/'`). A URL that matches no product thus resets the context to "no current App".
* *Where the base URL comes from:* the route `url` / `baseUrl` values come from the Workspace-config BFF (`loadWorkspaceConfig`, Unit 2). The Shell's own BFF clients point at `./shell-bff` (the `BASE_PATH` provided in link:{shell}/src/app/app.module.ts[`app.module.ts`]). `ConfigurationService` (Unit 2) resolves runtime keys such as `APP_BASE_HREF` from the `${PLACEHOLDER}`-templated link:{shell}/src/assets/env.json[`env.json`]. The API base URL is thus a *runtime, workspace- and route-driven* value, not a build-time constant.

== Angular / React

* Angular: a generated client extends or composes `PortalApiConfiguration` to get its `basePath`. Apps that only need the current App read `AppStateService.currentMfe$`.
* React: the libs have no `PortalApiConfiguration` equivalent. React Apps read `useAppState().currentMfe$` and build any base URL from `remoteBaseUrl` themselves. The context and its readiness contract are otherwise the same as in Angular.

== Edge cases & pitfalls

* *`basePath` is a placeholder until `currentMfe$` arrives.* It stays `./<apiPrefix>` until the first `currentMfe$` value (Unit 1 readiness). Code that reads it earlier, such as a request built in a very early lifecycle hook, gets the relative placeholder instead of a real host. Gate on `currentMfe$.isInitialized` if you need the resolved value synchronously.
* *The context resets on an unknown URL.* A route the Workspace does not define lands on the not-found page, which publishes a blank `MfeInfo`. An instance whose first value is blank resolves its base path from the empty `remoteBaseUrl` and keeps it. A later blank publish does not rewrite an instance that already consumed an App value. New per-`appId` lookups (`parameters`, new `PortalApiConfiguration` instances) resolve against empty `appId`/`remoteBaseUrl`; treat that state as "no current App".
* *`remoteBaseUrl` is the raw route `url`, not `baseHref`.* `baseHref`/`mountPath` are the joined `baseUrl`. They normally agree, but the API base URL follows `remoteBaseUrl`.
* *`basePath` cannot be set.* The setter throws `Error('Do not set basePath')`; a generated client must use the resolved value.

== Debugging

* Log `currentMfe$` where the base URL is resolved. An empty `remoteBaseUrl` means the not-found page, or no product navigated into yet. A `basePath` still at `./<apiPrefix>` means the first `currentMfe$` has not arrived.
* Check `currentMfe$.appId` / `productName` against the BFF route you expect.
* For raw cross-App Topic traffic (including `currentMfe`), see Area 13 (Diagnostics): `tracing-communication.adoc`.

== Known issues

* *Reading `basePath` before the first `currentMfe$` returns the placeholder.* `PortalApiConfiguration.basePath` is `./<apiPrefix>` until the first `currentMfe$` value maps into `basePath$` (link:{libs}/angular-utils/src/lib/utils/portal-api-configuration.utils.ts[`portal-api-configuration.utils.ts`]). The setter throws, so the value is always the resolved one. Wrong values come from the placeholder window, or from a blank first publish that resolves an instance to the empty-base path instead of a product host. Also recorded in Unit 2.
* *Misspelled `encocdeParam` accessor.* The same file names the setter `encocdeParam` instead of `encodeParam`, so `configuration.encodeParam` cannot be reassigned through the intended accessor. Also recorded in Unit 2.
