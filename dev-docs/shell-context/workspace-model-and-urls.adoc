== Question answered

What is the Workspace model the Shell hands to an App, and how does an App build a correct URL for another product's route or endpoint from it?

== Why it exists

An App often deep-links into a *different* product in the same Workspace, such as "open the customer with id 42 in the Sales app". It cannot hard-code a host or path, because these URLs depend on the loaded Workspace (portal), the products registered in it, and the layout of each product's routes and endpoints.

The Workspace model carries this data, and a few pure helpers turn it into URLs. The model reaches the App on a Topic and the helpers are framework-agnostic, so Angular Apps, React Apps and the Shell, which builds its route table from the same model, resolve URLs the same way. link:workspace-config-loading.adoc[Workspace config load & distribution] covers loading and publishing the model; link:context-readiness.adoc[Context overview & readiness] covers waiting for it.

== How it works

The Workspace is published on the link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/current-workspace.topic.ts[`current-workspace` Topic] (registered with the raw name `currentPortal`, version 1). Its value is the link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/workspace.model.ts[`Workspace`] model:

* `baseUrl`: the Workspace root and the fallback base when a route has none.
* `workspaceName` / `portalName`: the Workspace name. `portalName` is deprecated in favour of `workspaceName`.
* `routes`: an array of link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/route.model.ts[`Route`]. Each `Route` is one product/app entry point: `appId`, `productName`, `baseUrl`, `url`, `remoteEntryUrl`, `exposedModule`, `pathMatch`, … and `endpoints`.
* `endpoints`: on each route, an array of link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/endpoint.model.ts[`Endpoint`] of shape `{ name?, path? }`.
* `homePage`, `i18n`, `displayName`, and several deprecated fields (see Edge cases).

URL building lives in pure functions in link:{libs}/integration-interface/src/lib/utils/workspace.utils.ts[`workspace.utils.ts`], shared by both frameworks:

* `constructRouteUrl(workspace, appId, productName, endpointName?, endpointParameters?)` → the full URL.
* `doesUrlExistForWorkspace(workspace, productName, appId, endpointName?)` → `boolean`: whether a matching route or endpoint exists.

`constructRouteUrl` resolves in four steps:

. *Match the route*: `filterRouteFromList` picks the `Route` whose `appId` and `productName` both match. With no match, it warns and returns the Workspace `baseUrl`. With several matches, it warns and uses the first.
. *Pick the base*: the route's `baseUrl` if set, otherwise the Workspace `baseUrl`. Without an `endpointName`, this is the result.
. *Resolve the endpoint*: `constructEndpointUrl` → `dissolveEndpoint` finds the endpoint by `name` and follows `[[alias]]` chains: an endpoint whose `path` contains `[[other]]` is replaced by the endpoint named `other`. `fillParamsForPath` then fills `{param}` placeholders from `endpointParameters`.
. *Join*: `joinWithSlash` joins base and endpoint path with a single slash.

[source,mermaid]
----
flowchart TD
  I["constructRouteUrl(workspace, appId, productName, endpointName?, params?)"]
  I --> R["filterRouteFromList: match appId + productName"]
  R -->|no route| B["warn + return workspace.baseUrl"]
  R -->|route found| RB["base = route.baseUrl or workspace.baseUrl"]
  RB -->|no endpointName| OUT1["return base"]
  RB -->|endpointName| EP["dissolveEndpoint: resolve name + alias chain"]
  EP --> FP["fillParamsForPath: replace {param} from params"]
  FP --> OUT2["joinWithSlash(base, endpointPath) → URL"]
----

== Libs side / Shell side

=== Libs side

The libs provide the model, the pure helpers, and a thin reactive consumer per framework.

* link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/workspace.model.ts[`Workspace`], link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/route.model.ts[`Route`], link:{libs}/integration-interface/src/lib/topics/current-workspace/v1/endpoint.model.ts[`Endpoint`]: the data shape, in `integration-interface`.
* link:{libs}/integration-interface/src/lib/utils/workspace.utils.ts[`workspace.utils.ts`]: the framework-agnostic builders. `constructRouteUrl` and `doesUrlExistForWorkspace` are the entry points. `filterRouteFromList`, `constructBaseUrlFromWorkspace`, `dissolveEndpoint`, `fillParamsForPath` and `joinWithSlash` are the steps. The entry points take an optional `warn` handler (default `console.warn`) and pass it down. They warn and *degrade instead of throwing* (see Edge cases).
* link:{libs}/angular-integration-interface/src/lib/services/workspace.service.ts[`WorkspaceService`]: the Angular consumer. `getUrl(productName, appId, endpointName?, endpointParameters?)` and `doesUrlExistFor(productName, appId, endpointName?)` map `AppStateService.currentWorkspace$` through the helpers and return `Observable<string>` / `Observable<boolean>`. Both pass `logger.warn` as the `warn` handler.
* link:{libs}/react-integration-interface/src/lib/contexts/useWorkspace.ts[`useWorkspace`]: the React equivalent. It reads `useAppState().currentWorkspace$` and must be called inside an `AppStateProvider`.

=== Shell side

The Shell produces the model. In link:{shell}/src/app/app.module.ts[`app.module.ts`], `workspaceConfigInitializer` calls `publishCurrentWorkspace`, which publishes to `currentWorkspace$` the fields an App needs for URL building: `baseUrl`, `portalName`, `workspaceName`, `routes`, `homePage`, `microfrontendRegistrations: []`, `displayName` and `i18n`. The values come from the `loadWorkspaceConfigResponse` of the Workspace-config BFF.

The Shell builds its own Angular route table from the same `routes` list. `RoutesService.init(...)` → `convertToRoute` in link:{shell}/src/app/shell/services/routes.service.ts[`routes.service.ts`] turns each BFF route into an Angular route whose `canActivateChild` wires up the app. One `Workspace.routes` list therefore drives both Shell navigation and every App's cross-App deep links, with no second source of truth.

== Angular / React

Resolution is identical: both frameworks call the same pure helpers on the same `Workspace` value.

* Angular: inject `WorkspaceService`; `getUrl` / `doesUrlExistFor` take `(productName, appId, ...)` and return Observables.
* React: `useWorkspace()` returns `{ getUrl, doesUrlExistFor }` with the same signatures. Components or hooks consume the returned Observables.

Both read `currentWorkspace$` and inherit its readiness contract: gate on `isInitialized` before the first value, or use `asObservable()`, which already filters on readiness (see link:context-readiness.adoc[Context overview & readiness]).

== Edge cases & pitfalls

* *Argument order differs between the two helpers.* The service and hook methods all take `productName` first. The pure helpers do not agree: `constructRouteUrl(workspace, appId, productName, …)` takes `appId` first, and `doesUrlExistForWorkspace(workspace, productName, appId, …)` takes `productName` first. The services and hooks pass them correctly, so only direct calls to the helpers are at risk.
* *Ambiguous product/app.* If two routes share the same `appId` + `productName`, `filterRouteFromList` warns ("more than one route. First route has been used.") and uses the first.
* *Missing route / endpoint / parameter.* Nothing throws; each gap falls back to a base URL:
** no route → the Workspace `baseUrl`, or `''` if the Workspace has none;
** no endpoint or an empty `endpoint.path` → the route base URL;
** a `{param}` without a value → the endpoint path is dropped and the route base URL is returned.
* *`[[alias]]` chains.* `dissolveEndpoint` follows aliases until it reaches a concrete endpoint. A missing closing `]]` or an unknown alias name resolves to `undefined`, which falls back to the route base URL with a warning. A self-referencing or cyclic alias never resolves; see Known issues.
* *Other `Workspace` fields are deprecated.* Use `baseUrl`, `workspaceName`, `routes`, `homePage` and `i18n`.
* *The Topic is named `currentPortal`.* `CurrentWorkspaceTopic` registers under the raw name `currentPortal` (v1). If App and Shell disagree on this name or version, the App never receives the model. link:context-readiness.adoc[Context overview & readiness] covers the readiness mechanics.

== Debugging

* *Read the warnings.* The services pass `logger.warn` to the resolvers. Enable the `WorkspaceService` / `useWorkspace` logger to see which route, endpoint or parameter was missing when a URL resolved to a base URL.
* *Confirm the model arrived.* Gate on `currentWorkspace$.isInitialized` and log the `routes` you received. A URL that keeps resolving to the Workspace base usually means your `appId`/`productName` matches no `routes` entry.
* *Compare the identifiers.* Check `workspace.routes` (from the BFF) against the `appId`, `productName` and `endpointName` you pass. `appId` and `productName` must match exactly as strings.

== Known issues

* *Cyclic `[[alias]]` loops forever.* In link:{libs}/integration-interface/src/lib/utils/workspace.utils.ts[`dissolveEndpoint`], an endpoint whose `path` is `[[self]]` (its own name), or two endpoints that alias each other, keep the `while` loop running because nothing tracks visited names. This looks wrong because every other malformed input degrades to a base URL with a warning.
