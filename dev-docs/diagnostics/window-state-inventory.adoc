== Question answered

Which pieces of state do the libraries (and the Shell) keep on the shared `window`/`globalThis` object — and who writes, who reads, and which Area owns each of them?

== Why it exists

A OneCX page hosts the Shell, several Apps and Remote Components, all from different bundles, on one `window`. Several mechanisms cannot use a normal in-process channel because they have to cross that bundle boundary in the *same* page, or they have to survive a re-render. So they keep their state on global properties — plain keys on `window`/`globalThis`.

That is powerful and dangerous at the same time:

* any bundle can read or clobber a key without a type-system or ownership contract;
* the value is shared across *all* frameworks on the page, so an Angular write and a React read see the same object;
* nothing in the code tells you what is *supposed* to be there.

This inventory is the reference for "what actually lives on `window` in a running OneCX page". Every entry is verified against the current code; every key names its owning Area so you know where to go for the mechanism. The *Owning Area* column points at the Area from the Dev Docs index that explains the mechanism — this Unit does not re-explain it.

== How it works

Global keys in OneCX come in two shapes.

* **Namespaced objects.** A single top-level key that holds a subtree, written through link:{libs}/accelerator/src/lib/utils/ensure-property.utils.ts[`ensureProperty`]. `ensureProperty(globalThis, ['@onecx/accelerator', 'topic', 'tabId'], value)` creates each intermediate object if missing and only assigns the leaf when it is `null`/`undefined`, so a later call never clobbers an earlier one. `@onecx/accelerator`, `@onecx/integration-interface`, `@onecx/angular-utils` and `onecxAuth` are this kind.
* **Plain scalar / map keys.** A single top-level key with a scalar or flat object — `onecxMessageId`, `onecxIcons`, `onecxTranslations`, `onecxTriggerElement`, `onecx-shell-capabilities`.

Both kinds are *shared across the page*: a value written by the Shell is read by an Angular App and a React App on the same `window`, with no per-bundle copy.

== Libs side / Shell side

=== Libs side

Most globals are *owned* by a library in this repository: the library writes the key through `ensureProperty` and also reads it back. The exceptions — the auth proxies and the Shell capability flags — are *written by the Shell* and *read by the libraries* (or, for `onecxAngularAuth`, written by the Shell for older libraries). The table below records, per key, the owner and whether the writer and reader are on the libs side or the Shell side.

=== Shell side

The Shell writes three kinds of globals. It sets the auth proxies (`onecxAuth`, `onecxAngularAuth`) from the `AuthServiceWrapper` that the `@onecx/shell-auth` library instantiates when the Shell calls `provideAuthService()`; it publishes the capability list via `ShellCapabilityService.setCapabilities(...)` in link:{shell}/src/bootstrap.ts[`src/bootstrap.ts`]; and at startup it exposes the Module Federation instance on `globalThis` and initialises the preloader registry in link:{shell}/src/main.ts[`src/main.ts`]. The libs never need to know *how* the Shell produced these values — only the key name.

One related value is not a `window` key but is equally important at runtime:

* `localStorage.debug` — the namespace patterns that enable link:logging.adoc[logging]. Written by the developer, read by the `debug` package on load.

== Angular / React

Both frameworks share the same globals. Angular writes and reads `onecxTranslations` and `onecxAuth` (via `angular-auth`); React reads `onecxTriggerElement` and the Module Federation instance. `onecxIcons` and the `@onecx/accelerator.*` / `@onecx/integration-interface.*` keys are consumed by both, which is exactly why they live on `window` rather than in a single framework's store.

== Edge cases & pitfalls

* *No ownership guarantee.* Nothing stops a bundle from overwriting another's key. `ensureProperty` only protects against *first-writer-wins* on the leaf; it does not protect a key from being replaced wholesale. Treat the table above as the intended surface and inspect it before debugging.
* *Values may not exist yet.* Most keys are created lazily with `??=`. Reading a key before its writer runs returns `undefined`; the auth reader in `angular-auth` handles this with a no-op default and a rejecting promise (`Error: No authServiceWrapper provided...`).
* *`@onecx/angular-utils.guards.debug` is an unused declaration.* The guards package declares the global, but the current code does not write or read it. Guard logging is enabled through the logger namespace instead: `localStorage.debug = '@onecx/angular-utils:guards-utils:*'`.
* *`onecxAngularAuth` is legacy.* It exists only so older library versions keep working. New code should read `onecxAuth`; the Shell writes both from the same `AuthServiceWrapper`.
* *Two `@onecx/*` look-alikes.* `@onecx/accelerator` (accelerator lib) and `@onecx/integration-interface` / `@onecx/angular-utils` are separate top-level keys with unrelated sub-trees.

== Debugging

In DevTools you can inspect the live values without a page reload:

[source,js]
----
// The whole accelerator namespace (topics, tab id, gatherer promises, stats)
globalThis['@onecx/accelerator']

// Topic statistics — turn these on first, they are off by default
globalThis['@onecx/accelerator'].topic.statsEnabled = true

// Auth proxies the Apps read
globalThis.onecxAuth

// Shell-advertised capabilities
globalThis['onecx-shell-capabilities']

// Module Federation instance the Apps load remotes through
globalThis.onecxFederationInstance
----

To see *why* a key has a given value, enable link:logging.adoc[logging] and follow the owning Area. To see the values *change* as Topics move between Apps, use link:tracing-communication.adoc[Tracing cross-App communication].

== Known issues

* *The Shell does not advertise or answer the dynamic-translations capability.* `link:{shell}/src/bootstrap.ts[bootstrap.ts]` calls `setShellCapabilities([PARAMETERS_TOPIC, CURRENT_LOCATION_TOPIC, ACTIVENESS_AWARE_MENUS])` but does *not* include `DYNAMIC_TRANSLATIONS_TOPIC`, even though link:{libs}/integration-interface/src/lib/services/dynamic-translation.service.ts[`dynamic-translation.service.ts`] checks `hasShellCapability(ShellCapability.DYNAMIC_TRANSLATIONS_TOPIC)` before using the dynamic-translations Topic. The global cache `@onecx/integration-interface.dynamicTranslationsCache` is still created, but the capability the libs look for is absent on `main`. Follow-up: either the Shell advertises and answers the Topic, or the lib check is removed. (Owned by *10. Localization*.)
