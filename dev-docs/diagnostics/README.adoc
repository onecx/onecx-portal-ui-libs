== Problem

A running OneCX page is a single browser page that hosts the Shell plus one or more Apps and Remote Components, all loaded from different bundles. When something is off — a Topic that never updates, a missing translation, a token that is not attached to a request, styles bleeding across Apps — the state you need to inspect is spread across several runtime mechanisms at once: the browser console, a set of `window`-level globals the libraries share, and the Topic/BroadcastChannel traffic that carries state between the Apps and the Shell.

This Area collects the tools for looking inside that running page. It does not re-explain the owning mechanisms (Topics, authentication, translations, styling); it points at them and gives you the concrete way to observe each of them at runtime.

== Big picture

Every diagnostic signal in OneCX comes from the same two places: the libraries in this repository, and the Shell. The libraries own the mechanisms (the logger factory, the `window` globals, the `Topic` and `TopicPublisher` classes); the Shell consumes them and adds its own writes (auth proxies, capability flags, Module Federation instance). Because the Shell and the Apps share one `window` object and one event loop, the two sides are observable from the same DevTools session.
