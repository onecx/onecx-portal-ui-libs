This Area explains how a URL is decided and acted on in a OneCX page: how a single address bar is turned into one shared URL that every application's router follows, and how the Shell uses that URL to choose which application to open (the *Current App*) and to show a page when nothing owns the URL.

toc::[]

== Problem

A OneCX page holds several applications at once — a Shell and one or more Angular or React apps, each with its own router. Yet there is only one address bar and one `window.location`. Two hard problems follow:

* *Everyone has to agree on the URL.* Any app can navigate, and the browser's back/forward can change the URL without any app's cooperation. If each router only managed its own slice, the routers would drift apart and disagree about "where am I".
* *The Shell has to decide what to open.* The Shell does not know its own routes at build time; they arrive at runtime with the Workspace. It must build a route table, match the current URL against it, load the one application that owns that URL, and fall back to a not-found page when no one does.

Solved together, these give the navigation contract of the page: the URL is the single source of truth, and every router follows it — the Shell's router follows it to *activate* an app, and each app's router follows it to *stay in sync*. Whether a cross-app navigation is even *allowed* is a separate concern (Units 4–6) handled by guards, on top of this.

== Big picture

The Shell is the publisher of the shared URL and the owner of the route table. Apps are subscribers that drive their own routers from that URL. The split of work:

[source,mermaid]
----
flowchart LR
  subgraph Shared
    URL[window.location / address bar]
  end
  subgraph Shell
    Patch[patched history]
    Listener[urlChangeListenerInitializer]
    Routes[RoutesService route table]
    Match[Angular Router match]
  end
  subgraph Topics
    LOC[current-location]
    MFE[current-mfe]
  end
  subgraph Apps
    A[App A router]
    R[App B router]
  end
  URL <--> Patch
  Patch --> LOC
  Listener --> LOC
  LOC --> A
  LOC --> R
  Routes --> Match
  Match --> MFE
  MFE --> A
  MFE --> R
----

Reading it: a real navigation lands on `window.location`; the Shell's patched history turns it into a `current-location` broadcast; the Shell's own listener and every app's router follow that URL; the Shell's `RoutesService` matches the URL to a route and publishes the resulting `current-mfe` (the Current App), which the apps use to scope their own routing.
