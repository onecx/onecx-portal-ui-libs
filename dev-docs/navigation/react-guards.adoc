== Question answered

How does the cross-App guard protocol (Unit 4) get implemented on the React side: how a React app's route guards (declared on the route `handle`) are collected and run mode-aware, and how the `useGuardsGatherer` / `useWrappedGuards` / `useGuardCheck` / `useGuardDeactivation` hooks, plus the `guardCheckKey` flag, stand in for the Angular `WebcomponentConnector`?

== Why it exists

Unit 4 fixes the *protocol*: a navigation carries a `GuardsNavigationState`, a `GuardsNavigationStateController` maps it to a `GUARD_MODE`, and a `GuardGatherer` collects each other app's boolean verdict before the shared URL may move. That protocol is framework-agnostic. React supplies its own concrete pieces: guards are declared on the React Router route `handle` (not on a route `Route` config), the router is driven by React's `useNavigate`, and there are no Angular router events to subscribe to. This Unit documents those React specifics: the plain-class `GuardsGatherer` / wrappers (no `@Injectable`, no injected `Router`), `wrapGuards` which collects the guards from the current route `matches` into callable helpers, and the four hooks that let an app wire the protocol into its component tree. The `guardCheckKey` flag is a React-only addition. The Angular-side equivalents (`Route` guards, `WebcomponentConnector`, the `revertNavigation` publisher) are Unit 5; the shared protocol is Unit 4.

== How it works

The React implementation is a set of plain classes plus hooks; there is no `WebcomponentConnector` analogue in the React libs. The app composes the pieces itself: it creates a gatherer tied to its own `navigate` function, then builds wrapped guard helpers from its current route matches, and runs the activation / deactivation checks in response to location changes.

=== Collecting the route guards (`wrapGuards`)

link:{libs}/react-utils/src/lib/guards/utils/wrap-guards.utils.ts[`wrapGuards`] does not mutate route config the way the Angular version does. Instead it *collects* the guards that are already declared on the matched routes and returns them as ready-to-run helpers. It takes `options` (`matches`, `location`, and optionally `guardsNavigationState`, `guardsGatherer`, `guardsNavigationStateController`) and:

. *Reads the guards from the route `handle`.* link:{libs}/react-utils/src/lib/guards/utils/guard-handles.utils.ts[`getGuardsFromMatches`] walks the `UIMatch[]` and, for each match, reads `match.handle` as a link:{libs}/react-utils/src/lib/guards/utils/guard-handles.utils.ts[`GuardsHandle`], `{ canMatch?, canActivate?, canActivateChild?, canDeactivate? }`, and concatenates each array into one list. A React app declares its guards in the route `handle` rather than in the `Route` object.
. *Builds wrapper helpers.* It constructs one `ActivateGuardsWrapper` and one `DeactivateGuardsWrapper` (plain classes, given the gatherer and controller) and returns a link:{libs}/react-utils/src/lib/guards/utils/wrap-guards.utils.ts[`WrappedGuards`] object with four async helpers: `canMatch()`, `canActivateChild()`, `canActivate()` (all delegate to the activate wrapper with the matching guard list) and `canDeactivate(nextLocation)` (delegates to the deactivate wrapper). Each helper calls its wrapper with a `GuardExecutionContext` built from `matches` and `location` (`params` taken from the last match); the deactivation context also carries `nextLocation`.

So instead of replacing route guards with a wrapper (Angular), React exposes the collected guards as functions the app invokes. The four helper kinds map to React Router's guard lifecycle, with an extra `canMatch` pre-`canActivate` stage.

=== The mode-aware wrappers

link:{libs}/react-utils/src/lib/guards/utils/activate-guards-wrapper.utils.ts[`ActivateGuardsWrapper`] and link:{libs}/react-utils/src/lib/guards/utils/deactivate-guards-wrapper.utils.ts[`DeactivateGuardsWrapper`] are plain classes (constructed with the optional gatherer and a `GuardsNavigationStateController`). Each takes a guard list and the `GuardsNavigationState`, reads the mode via `getMode`, and branches on it. Both resolve each guard through `resolveToPromise` (Promise / plain value), defaulting a guard that throws to `true`, and short-circuit to `true` when the guard list is empty. The branch is:

[cols="1,2,1", options="header"]
|===
|Mode |What the wrapper does |Combine
|`INITIAL_ROUTER_SYNC` |Run the own guards for the current route. |`combineToBoolean`
|`ROUTER_SYNC` |Run the own guards, then *always* return `true` via `executeRouterSyncGuard()`: the URL has already moved and is agreed, so the outcome cannot veto it. |`combineToBoolean`
|`GUARD_CHECK` |Run the own guards for the target route as a check. If the result is `false`, immediately `guardsGatherer?.resolveRoute(futureUrl, false)`: this app vetoes the requesting app. If `true`, the positive verdict is resolved later by the caller (see *Wiring*). |`combineToBoolean`
|`NAVIGATION_REQUESTED` |Wait on the `guardCheckPromise` stored on the state (the other apps' verdicts). If it resolves `false`, return `false` and skip the own guards. If it resolves `true`, run the own guards and return their result. A missing promise defaults to `true` (allow). |`combineToBoolean`
|===

Unlike Angular, the React wrappers combine only to a boolean in every mode: the React `GuardResult` is `boolean`, there is no `UrlTree` / `RedirectCommand` pass-through (see link:{libs}/react-utils/src/lib/guards/utils/guard-types.utils.ts[`guard-types.utils.ts`], link:{libs}/react-utils/src/lib/guards/utils/guards-utils.utils.ts[`guards-utils.utils.ts`]).

=== The fake navigation (`GuardsGatherer`)

link:{libs}/react-utils/src/lib/guards/services/guards-gatherer.ts[`GuardsGatherer`] is a plain class (no `@Injectable`) constructed with the React Router `NavigateFunction` (and, optionally, a controller). When *another* app asks this app to check its guards, the registered gatherer callback (`executeGuardsCallback`) performs a *fake* `navigate(routeUrl, { state: createGuardCheckState(undefined, guardCheckKey), replace: true })` that updates the active router location while replacing the current history entry, then lets `useGuardCheck` evaluate after that location change. It stores a resolver in a `guardsChecks` map keyed by the normalised URL. The wrapper resolves the map with `false` on a veto; the caller resolves it with `true` on success. `gather` / `resolveRoute` normalise the URL (leading `/`, strip a trailing `/`) so a request and its verdict always map to the same key.

=== Wiring it up (the hooks)

Because there are no router events to subscribe to, the app wires the protocol into its component tree with hooks from `@onecx/react-utils/guards`:

. *link:{libs}/react-utils/src/lib/guards/hooks/use-guards-gatherer.ts[`useGuardsGatherer`]*: creates a `GuardsGatherer` bound to the current `useNavigate()` (memoised on `navigate`) and, when `activate` is not disabled, `activate()`s it on mount and `deactivate()`s it on unmount.
. *link:{libs}/react-utils/src/lib/guards/hooks/use-wrapped-guards.ts[`useWrappedGuards`]*: reads `useMatches()` and `useLocation()` and memoises `wrapGuards(...)` over them, exposing the `WrappedGuards` helpers to the component.
. *link:{libs}/react-utils/src/lib/guards/hooks/use-guard-check.ts[`useGuardCheck`]*: on each change of `location.key` (when `enabled`), runs the activation chain `canMatch().then(canActivateChild).then(canActivate)` and reports the result via `onGuardCheck`. This is where a React app performs its activation guard checks as the location moves.
. *link:{libs}/react-utils/src/lib/guards/hooks/use-guard-deactivation.ts[`useGuardDeactivation`]*: runs `canDeactivate(nextLocation)` for a given target location and reports the result, the deactivation counterpart.

In `NAVIGATION_REQUESTED` mode the app (or its navigation code) drives the cross-app step: it calls `guardsGatherer.gather({ url })`, collapses the returned verdicts with `combineToBoolean`, and stores the promise on the navigation state via `createNavigationRequestedState`: the same promise the `NAVIGATION_REQUESTED` branch of the wrappers waits on. As with Angular, the positive `GUARD_CHECK` verdict (the `resolveRoute(url, true)` and the cancel of the fake navigation) is the caller's responsibility, and the Shell-side `revertNavigation` on a rejected initial sync is handled by the Shell rather than the React guard libs.

== Libs side / Shell side

=== Libs side

Everything the app needs is in `@onecx/react-utils/guards`:

* *The model & controller.* link:{libs}/react-utils/src/lib/guards/model/guard-navigation.model.ts[`guard-navigation.model.ts`] (`GuardsNavigationState`: including `guardCheckKey`, the flag constants, the `GUARD_MODE` const object and the `GuardMode` type) and link:{libs}/react-utils/src/lib/guards/services/guards-navigation-controller.ts[`GuardsNavigationStateController`] (`getMode`, the `create*State` helpers, `createGuardCheckState(state?, guardCheckKey?)`).
* *The wrappers & helpers.* `ActivateGuardsWrapper`, `DeactivateGuardsWrapper`, `wrapGuards` / `WrappedGuards`, `getGuardsFromMatches` / `GuardsHandle`, the guard type definitions, and `combineToBoolean` / `executeRouterSyncGuard` / `resolveToPromise` in the `guards` utils.
* *The gatherer.* `GuardsGatherer` (fake navigation via `navigate`, `guardsChecks` map, `guardCheckKey` counter, URL normalisation).
* *The hooks.* `useGuardsGatherer`, `useWrappedGuards`, `useGuardCheck`, `useGuardDeactivation` (re-exported from `use-guards.ts`).

=== Shell side

The Shell participates at one point only: it *responds* to the `revertNavigation` event when an app's initial router sync is rejected (the patched-history / listener code in link:{shell}/src/app/app.module.ts[`app.module.ts`] calls `history.back()`). The Shell does not itself run React guard checks. (The Angular `WebcomponentConnector` is the one that publishes `revertNavigation`; the React guard libs contain no such publisher: that signal is raised by the app/Shell wiring, and the Shell's handling is the same.)

== Angular / React

This Unit is the React-specific half; Unit 5 covers the Angular plumbing. The real differences, each fixed here:

* *Where guards live.* Angular reads `Route` guards (`canActivate` / `canDeactivate` / `canActivateChild`) and replaces them with a wrapper. React reads route `handle` guards (`canMatch` / `canActivate` / `canActivateChild` / `canDeactivate`) and returns them as callable helpers: there is an extra `canMatch` stage and no route mutation.
* *No connector.* Angular's `WebcomponentConnector` subscribes to `RoutesRecognized` / `GuardsCheckStart` / `GuardsCheckEnd` and drives wrap / gather / finalise automatically. React has no such connector; the app composes the four hooks and calls `gather` itself.
* *`guardCheckKey`.* React adds a `GUARD_CHECK_KEY` state flag. Each fake navigation is given a fresh key from an incrementing counter (`getNextGuardCheckKey`), so a guard check on the *same* URL is still re-processed rather than deduplicated: Angular relies on `onSameUrlNavigation: 'reload'` for the same-URL case instead.
* *Injection vs plain classes.* The Angular gatherer is `@Injectable({ providedIn: 'root' })` and injects `Router` / `Injector`. The React gatherer and wrappers are plain classes passed their `NavigateFunction` and (optionally) a controller.
* *Result type.* The Angular `GuardResult` can be `UrlTree` / `RedirectCommand`, so `NAVIGATION_REQUESTED` uses `combineToGuardResult`. The React `GuardResult` is `boolean`, so every mode uses `combineToBoolean`.

The protocol, the four modes, the Gatherer round trip and the `revertNavigation` signal are identical in both and are fixed in link:why-cross-app-guards.adoc[Why cross-App guards].

== Edge cases & pitfalls

* *The fake navigation updates the active location.* The `GUARD_CHECK` navigation uses `replace: true`, which replaces the current history entry while changing the active router location; `useGuardCheck` then runs after that location change. The library does not automatically block or roll back that navigation, so consumer integration must handle the verdict and any route recovery.
* *`guardCheckKey` is what makes same-URL checks repeat.* Because a guard check navigates to a URL that is often already the current one, React stamps each check with a fresh `guardCheckKey`. Code that compares two guard-check navigations on the URL alone will see them as identical and may skip the second one.
* *A missing `guardCheckPromise` defaults to allow.* In `NAVIGATION_REQUESTED`, if the promise is absent from the state the wrapper logs a warning and uses `Promise.resolve(true)` rather than block.
* *`ROUTER_SYNC` cannot veto.* In `ROUTER_SYNC` mode the wrapper returns `true` via `executeRouterSyncGuard()` regardless of the guards' outcome: the same behaviour as Angular.
* *Guards are declared on the `handle`, not the `Route`.* A guard placed in the wrong place on the route object is silently ignored by `getGuardsFromMatches`, which only reads `match.handle`.
* *Guards run in a fixed order.* `useGuardCheck` runs `canMatch` → `canActivateChild` → `canActivate` in sequence, short-circuiting on the first `false`. A `canMatch` veto therefore suppresses the later stages.
* *The gatherer throws when not active.* `gather` / `resolveRoute` / `executeGuardsCallback` throw `Guards gatherer is not active` if called before `activate()` (or after `deactivate()`); `useGuardsGatherer` manages that lifecycle.

== Debugging

* *Enable the guard logs with the `debug` package.* The React guard code logs through the `debug` namespace `@onecx/react-utils:guards` (built by `createLoggerFactory`). In the DevTools console set `localStorage.debug = '@onecx/react-utils:guards*'` and reload to see the mode and each guard-check callback as it runs.
* *Watch the verdict traffic.* The cross-app verdicts ride on the `GuardGatherer` gatherer, whose `debug` namespace is `@onecx/accelerator:Gatherer:GuardGatherer` (request `{ url }`, response `boolean`). See Area 13 (Diagnostics: `tracing-communication.adoc`).
* *The old one-line switch was Angular-only.* The old guard-debug page (`dev-docs/guards/`, removed) documented `window['@onecx/angular-utils'].guards ??= { debug: true }`. That property is still written (see link:{libs}/angular-utils/guards/src/declarations.ts[`declarations.ts`]) but no guard code reads it: logging is driven by `localStorage.debug` instead. See *Known issues*.

== Known issues

* *The documented guard debug switch is inert.* The old `dev-docs/guards/` debug page (now removed) told readers to set `window['@onecx/angular-utils'].guards ??= { debug: true }` to enable guard debug logs. In the current code that flag is never read: the guard loggers are created with `createLoggerFactory` (namespaces `@onecx/angular-utils:guards` and `@onecx/react-utils:guards`) and are controlled by the `debug` package (i.e. `localStorage.debug`), not by that `window` property (link:{libs}/angular-utils/guards/src/utils/logger.utils.ts[`angular logger.utils.ts`], link:{libs}/react-utils/src/lib/guards/utils/logger.utils.ts[`react logger.utils.ts`], link:{libs}/accelerator/src/lib/utils/create-logger.utils.ts[`createLoggerFactory`]). The `window['@onecx/angular-utils'].guards` object is still created as an empty placeholder (link:{libs}/angular-utils/guards/src/declarations.ts[`declarations.ts`]), so the documented command appears to run but has no effect. Documented here as the actual behaviour; enabling guard logs via the switch is a follow-up (PR).
* *`GUARD_CHECK` is not a non-committing flow yet.* The current `replace: true` navigation updates the active router location and replaces the current history entry, but it still relies on the consumer to decide how to handle the verdict and any route recovery. A genuinely non-committing guard-check flow is a follow-up implementation task.
