== Question answered

After the page is running, there are two different failures that look alike: a remote App module that failed to load, and a value published to the `globalError` Topic. What detects each one, and what does the page show for each?

== Why it exists

Bootstrap is over by the time either of these can happen: the workspace is configured and the Shell's viewport is on screen. Two failure classes remain. One is *local* to the Shell's router, a Micro-Front-End module it asked for could not be downloaded or instantiated. The other is *page-global*, anything on the page (an App, the Shell, a Remote Component) can publish an error to the `globalError` Topic and ask the whole page to show it. They are reached by different means and must not be conflated, so this Unit treats them as two distinct mechanisms with two distinct destinations.

== How it works

The two mechanisms do not share code. One is a navigation to a route; the other is a Topic-driven swap of the viewport's content.

. *App load failure.* The Shell's `RoutesService` loads a matched route's remote module through Module Federation's `loadRemote`. When the download or the first instantiation throws, the catch handler (`onRemoteLoadError`) fires a Portal Message (toast) and navigates to the route `remote-loading-error-page`, passing the requested application path as a route parameter. That route is lazy-loaded and renders the Shell's `ErrorPageComponent`, which shows the requested path and a reload action.
. *Global error.* Someone publishes a value (a `string` error code) to the `globalError` Topic. The Shell's viewport subscribes to that Topic; while a non-`undefined` value is present it renders the global-error component (`ocx-shell-error`) *in place of the whole viewport* instead of the normal route content. Clearing the value (publishing `undefined`) restores the normal viewport.

Because `globalError` is a Topic, it is page-global: the value is shared across every instance on the page within a tab. Any App can publish it; the Shell decides what it looks like. See Area 1 (Integration Contract & Topics) for the delivery mechanism.

== Libs side / Shell side

=== Libs side

The libraries provide the *signal* and reusable building blocks; they do not decide what failure is which.

* link:{libs}/integration-interface/src/lib/topics/global-error/v1/global-error.topic.ts[`GlobalErrorTopic`]: `Topic<string>`, name `globalError`, version 1. One error code for the whole page.
* The Angular `AppStateService` re-exposes it so a component injects one service and reads `globalError$`: link:{libs}/angular-integration-interface/src/lib/services/app-state.service.ts[`AppStateService`].
* A reusable error page for an App to render: link:{libs}/angular-accelerator/src/lib/components/error-component/global-error.component.ts[`GlobalErrorComponent`] (selector `ocx-error`). It reads the `err` code and `return` URL from the query string and offers a reload. Note this is the *library's* component, distinct from the Shell's own (see *Edge cases*).

=== Shell side

The Shell is the consumer that turns the signal into a concrete page.

* link:{shell}/src/app/shell/services/routes.service.ts[`RoutesService`] owns the App-load path: `loadChildren()` drives the module load, and `onRemoteLoadError()` fires the toast and navigates to `remote-loading-error-page` on failure.
* link:{shell}/src/app/app.routes.ts[`app.routes.ts`] registers the `remote-loading-error-page` route, lazy-loaded through `ErrorModule`.
* link:{shell}/src/app/error/components/error-page/error-page.component.ts[`ErrorPageComponent`]: the App-load failure page: reads the `requestedApplicationPath` route parameter, shows it, and reloads by setting `location.href` to the deployment path joined with that parameter.
* link:{shell}/src/app/shell/components/portal-viewport/portal-viewport.component.ts[`PortalViewportComponent`]: subscribes to `globalError$` in `ngOnInit`; a non-`undefined` value sets `globalErrMsg`, and the template swaps the viewport for `ocx-shell-error` while it is set.
* link:{shell}/src/app/shell/components/error-component/global-error.component.ts[`GlobalErrorComponent` (Shell)]: selector `ocx-shell-error`. Reads `err`/`return` from the query string (defaulting to `E1001_FAILED_START`), shows the code, and offers a *Try Again* reload.

== Angular / React

The `globalError` Topic and the failure *mechanisms* are framework-agnostic: any framework can publish to the Topic, and the Shell can navigate to the error route. The concrete pages in the current Shell and the `ocx-error` component are Angular. A React App would publish to the same `globalError` Topic and read it through link:{libs}/react-integration-interface/src/lib/contexts/appStateContext.tsx[`appStateContext`]; the mechanism is unchanged.

== Edge cases & pitfalls

* *Two different "global error" components.* The library exposes `ocx-error` (link:{libs}/angular-accelerator/src/lib/components/error-component/global-error.component.ts[`GlobalErrorComponent`]) and the Shell has its own `ocx-shell-error` (link:{shell}/src/app/shell/components/error-component/global-error.component.ts[`GlobalErrorComponent`]). They read the same `err`/`return` query parameters and default to the same `E1001_FAILED_START` code, but they are separate implementations. Do not assume the Shell uses the library's component.
* *App load failure vs. global error are different pages.* The App-load failure navigates to the `remote-loading-error-page` route (rendered by `ErrorPageComponent`, which shows the requested path and a reload action) and also fires a toast. A `globalError` value swaps the viewport to `ocx-shell-error` and fires no toast. They look similar but are different components reached by different means.
* *The `ocx-shell-error` query parameters are not the trigger.* The Shell's global-error component still reads `err`/`return` from the query string, but the *viewport* is driven by the `globalError$` value, not by a query string. An App publishes the Topic value to make the error appear; it does not navigate to a query-parameterised URL.

== Debugging

* *App-load failure.* The `loadRemote` call is bracketed by two log lines in link:{shell}/src/app/shell/services/routes.service.ts[`RoutesService`]: `➡ Load remote module <exposedModule>` before the download and `Load remote module <exposedModule> finished.` after a successful one. If the first appears without the second, the load failed. On failure `onRemoteLoadError` logs `Failed to load remote module: ${err}` (the `err` is the `loadRemote` rejection) and fires the `ERROR_MESSAGES.ON_REMOTE_LOAD_ERROR` toast; the page then shows the `requestedApplicationPath` that the failed load was trying to reach.
* *Global error.* The viewport subscribes to `globalError$` and logs `global error` on every non-`undefined` value (link:{shell}/src/app/shell/components/portal-viewport/portal-viewport.component.ts[`PortalViewportComponent`]). The code the `ocx-shell-error` page shows is the `string` on the Topic; read it from `window` or the Topic inspector to identify the App that published it. Because the viewport is Topic-driven, the error appears with no navigation: there is no route or query string to inspect.
* *Telling them apart.* A toast plus the `remote-loading-error-page` route means the module load failed. A viewport swap with no navigation and no toast means a `globalError` value is set.

General Topic and `window` inspection is in Area 13 (Diagnostics).
