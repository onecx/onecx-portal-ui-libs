How web components work

The browser-native primitives every part of this talk stands on

Primer · the primitive

A tag with a brain

how it looks in the DOM 
<ocx-workspace-component>
  … the whole workspace app,
      rendered right here …
</ocx-workspace-component>
an ordinary DOM node — like a <div>, but with behavior
→
what it really is 
class OcxWorkspaceComponent extends HTMLElement {
  connectedCallback() {  }    // "I'm in the DOM"
  disconnectedCallback() { }  // "I left the DOM"
}
The browser builds this class for you whenever it sees the tag.
No framework needed to use it. To the Shell it's just a node: createElement · append · remove.
Primer · step 1 of 2

customElements.define — teach the browser a tag

customElements.define(
  'ocx-workspace-component',
  OcxWorkspaceComponent
)
// register the name + the class
// the name must contain a "-"
After this…
the tag exists — but nothing is running yet
Define ≠ instantiate. define runs once per page, per name.
Register the same name twice → NotSupportedError.
so element names must be unique per page.
The app owns this.
It happens once, during bootstrap (Part 3 · Patches 6+7).
Primer · step 2 of 2

createElement + append — the app comes alive

// the Shell does this — it's all it does:
const el = document.createElement(
  'ocx-workspace-component')
// → plain node, nothing runs yet

wrapper.appendChild(el)
// → connectedCallback() fires
//   → the app starts (ngOnInit → connect)
the element's lifecycle
1createElement → node made, not yet connected
2append into the DOM → connectedCallback → app boots
3remove from the DOM → disconnectedCallback → app torn down
The app's whole lifetime = the element's time in the DOM. In → connectedCallback · out → disconnectedCallback.
Primer · why this matters

The app defines · the Shell instantiates

The Shell never touches the app's framework — it just makes a DOM node. Insertion is the boot signal.

There's a third web-component tool — Shadow DOM (style isolation). OneCX apps instead render into the light DOM and let the Shell scope their styles to the element.

Part 4 · summary

The navigation utilities — who owns what

Done centrally · you write none
  • Patched history → every URL change publishes CurrentLocationTopic (Shell)
  • isRouterSync → the echo breaker; followers move silently with replaceUrl
  • Shell follows → longest-first match picks the app, loads it, sets currentMfe$
  • WebcomponentConnector → initial router sync + follows the topic (via patched ngOnInit)
  • Route guards bridged across apps (Part 5)
You wire into the app
  • startsWith('') route matcher → makes your routes mount-path agnostic
  • initializeRouter (APP_INITIALIZER) → stamps mfeInfo/baseHref, prefixes string redirectTo, adds the ** catch-all
  • Your routes & provideRouter — the ordinary Angular setup
  • React: withSyncedRouter(App), SyncedRouterProvider, useSyncedLocation() / useAppHref()
The split is the point. Apps ship only their routes + two small helpers; all the cross-router sync stays in the Shell and the connector, so a new app inherits it for free.

Level 5 · tool 1 · request/response broadcast

The Gatherer

Generic accelerator primitive: ask all, collect all.
Every other instance pushes a promise synchronously, then answers via its callback.
The requester never answers itself.
Awaiting the publish guarantees all promises are registered before Promise.all.
GuardsGatherer = Gatherer named GuardGatherer
request {url} · response boolean
activated in connect(), off in disconnect()
