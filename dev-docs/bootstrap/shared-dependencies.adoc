== Question answered

When an App or Remote Component is built, how does OneCX decide *which* packages are shared and *into which share scope* they go, and what goes wrong at runtime when the shared versions or scopes do not line up?

== Why it exists

A OneCX page runs the Shell plus many independently built Apps in one JavaScript context. If every App bundled its own copy of the framework, one page would carry several copies of `@angular/core` / `react` and friends — wasted memory and the "two copies of the same library" bugs that break singletons. Module Federation (Unit 2) is the mechanism that shares packages instead of copying them. But sharing is only safe when it is *consistent*: an App must know, at build time, exactly which packages it expects to receive from the page, and the page must actually provide compatible copies of exactly those packages.

That consistency is what this Unit is about. OneCX centralises the decision in a single build-time helper — link:{libs}/build-utils/src/lib/get-onecx-shared-library-config.ts[`getOneCXSharedLibraryConfig`] — so that every App and Remote Component in the ecosystem shares the *same* set of scoped libraries, with `singleton: false` / `strictVersion: false` / `eager: false` as the helper defaults (effective configs can override them later; the Shell's per-loader configs do — see the Shell side). It makes two decisions per package: is it shared at all, and which scope it goes into with which flags. *Unit 2 states the share-scope rule at a high level; this Unit is the build-time deep dive* — how the generator computes each entry, and what a version or scope mismatch does when the App runs.

== How it works

The mechanism has a build-time half and a runtime half, and the invariant that ties them together is the **share scope**.

*Build time.* An application calls `getOneCXSharedLibraryConfig(dependencies, shouldGenerateSubDeps, options)` with its `package.json` `dependencies`. The generator turns that map into a `Record<packageName, SharedLibraryConfig>` — one `shared` entry per shared package — which the app passes into its Module Federation config. For every package it decides:

* *Shared at all?* Only packages whose name matches the `sharedLibraryPatterns` (Angular, OneCX, RxJS, PrimeNG, ngx-translate, ngrx, React, PrimeReact) are shared. A package that does *not* match is dropped from the shared map entirely — it is bundled privately into the app. So the framework and OneCX libraries are shared, and everything else is not.
* *Which scope?* The scope is computed from the app's *own* framework major, React first: if the app's `react` major is ≥ 19 it uses `react_<major>` (e.g. `react_19`); otherwise, if its `@angular/core` major is ≥ 21 it uses `angular_<major>` (e.g. `angular_21`); otherwise it falls back to `default`. The `requiredVersion` of each shared entry is the version the app declared for that dependency.
* *Which flags?* For every package that matched a pattern, `getOneCXSharedRecommendations` defaults to `singleton: false`, `strictVersion: false`, `eager: false`. This is the deliberate baseline that makes many framework versions coexist: nothing is forced to a page-wide single copy, so each scope can carry the copy an App was built against. Effective configs can override that baseline later (the Shell's per-loader configs do — see the Shell side).

*Runtime.* The Shell loads each App's remote with a `shareScope` — `toLoadRemoteEntryOptions` reads `r.shareScope` from the Workspace route and falls back to `'default'` when it is absent — and it loads the framework loaders (Unit 4) into the fixed scopes `default` / `angular_21` / `react_19`. When the App's remote is loaded, it resolves its shared packages out of that scope.

The load-bearing invariant: **the scope an app's packages are *built into* must match the scope the Shell *provides* (a preloaded loader) and the scope the remote is *loaded with*.** When they agree, the App resolves its framework packages from the page. When they do not, the App may resolve against a scope with no compatible copy of its framework and may not bootstrap.

== Libs side / Shell side

=== Libs side

The libraries provide the *generator* (build time) and the *runtime scope* (a field on the `Remote`).

* *The generator.* link:{libs}/build-utils/src/lib/get-onecx-shared-library-config.ts[`getOneCXSharedLibraryConfig(dependencies, shouldGenerateSubDeps, options)`] is the single entry point. Internally it:
. *Expands* each dependency into a main package plus, when `shouldGenerateSubDeps` is set, each exported sub-package read from the dependency's `package.json` (`exports`) — `generatePackageConfig` / `generateSubPackageConfig`.
. *Filters* every candidate through `packageFilterCallback` (default link:{libs}/build-utils/src/lib/get-onecx-shared-library-config.ts[`onecxPackageFilter`]): packages matching the dependency blacklist (`@nx*`, `@module-federation*`, `@onecx/build-utils*`) or the full-package blacklist (server/build-only sub-paths such as `@angular/common/locales/*`, `react-dom/server*`, `primeng/resources/`) are excluded.
. *Emits* a `SharedLibraryConfig` per surviving package: sets `requiredVersion` from the dependency map, computes the `shareScope` (the React-first rule above), then applies link:{libs}/build-utils/src/lib/get-onecx-shared-recommendations.ts[`getOneCXSharedRecommendations`]. If that returns `false` — the name matched no pattern — the reduce `return acc`s and the package is *omitted* from the map. Otherwise an optional `options.configCallback` may override any field (for example forcing `singleton: true` or, for the `@angular-architects/module-federation` toolchain, `includeSecondaries`/`requiredVersion: 'auto'`).
* *The recommendations.* link:{libs}/build-utils/src/lib/get-onecx-shared-recommendations.ts[`getOneCXSharedRecommendations(libraryName, sharedConfig)`] is the pattern gate. It tests the name against the `sharedLibraryPatterns` (`@angular*`, `@onecx*`, `rxjs*`, `primeng*`, `@ngx-translate*`, `@ngrx*`, `react*`, `primereact*`); on a match it sets `singleton = strictVersion = eager = false` and returns the config, otherwise it returns `false`.
* *The runtime scope.* link:{libs}/angular-utils/src/lib/utils/get-load-remote-entry-options.utils.ts[`get-load-remote-entry-options.utils.ts`] is where the scope is re-attached at runtime. `toLoadRemoteEntryOptions(r)` builds the `Remote` the Shell loads an App with and sets `shareScope: r.shareScope ?? 'default'`; `createRemoteConfig(entry, name, type, shareScope)` is the manual variant that defaults `shareScope` to `'default'`. So the scope the Shell loads a remote *in* comes from the Workspace data, not from a recomputation of the App's framework version.

=== Shell side

The Shell owns the *other half of the invariant* — it is what actually populates the scopes with the shared framework packages, and it is where the scope the App resolves against is fixed.

* *Loaders populate the scopes.* Each framework loader declared in link:{shell}/src/app/shell/utils/preloader.utils.ts[`preloader.utils.ts`] carries its own `shareScope` (`default` for the Angular 18/19/20 loaders, `angular_21` for the Angular 21 loader, `react_19` for the React 19 loader), and link:{shell}/src/main.ts[`main.ts`] registers and loads each loader remote into that scope. That is how the page gets the framework packages a `default`/`angular_21`/`react_19` App resolves against. The helper's `singleton: false` recommendation is only the default input to that process; the Shell's `pre_loaders/angular-21/module-federation.config.ts` overrides `@angular/*` to `singleton: true`, and `pre_loaders/react-19/module-federation.config.ts` does the same for `@onecx/*` plus a selected React package list. The loader mechanism itself — the five loaders, the `Promise.all` barrier, the failure handling — is Unit 4.
* *The remote is loaded with the Workspace scope.* When a matched route loads an App, the Shell builds the `Remote` with `toLoadRemoteEntryOptions` (libs), so `shareScope` is whatever the Workspace route declares (or `'default'`). Unit 5 covers this step in depth.

The Shell does not recompute an App's scope from its framework; it *trusts the Workspace* (`r.shareScope`) for the load and *provides the fixed loader scopes* for the resolution. Both must agree with what the App was built with.

== Angular / React

The scope rule (How it works) is the same for both frameworks but is *ordered* React-first:

* *React before Angular.* A React app is resolved first, so it can never land in an `angular_N` scope.
* *The practical effect.* Angular 18–20 pool into one `default` scope; Angular 21 and React 19 each get their own, so an Angular 21 app and a React 19 app resolve their framework from different scopes and never touch each other's copies (Unit 2).

== Edge cases & pitfalls

* *A non-matching package is silently not shared.* Because `getOneCXSharedRecommendations` returns `false` for a name that matches no pattern, the generator omits that package. Adding a new shared framework to the patterns is the only way it becomes shared; otherwise it is bundled privately into every App that depends on it.
* *Build scope and runtime scope must agree, and they are computed differently.* The build scope is derived from the App's own framework major; the runtime load scope comes from the Workspace route's `shareScope` (defaulting to `'default'`). A route that loads an Angular 21 App with `shareScope` absent (or the wrong value) loads that App into a scope that may not contain a compatible copy of the framework packages it was built against.
* *A framework major with no preloaded loader yields no verified provider for that scope.* The generator will happily emit `angular_22` for an App built against `@angular/core` 22, but the Shell only preloads `default`, `angular_21`, and `react_19` (Unit 4). There is no `angular_22` loader, so that scope is not pre-populated by the current Shell and an Angular 22 App may fail to resolve its framework if no compatible provider is otherwise available.
* *The helper's `singleton: false` default tolerates drift within a major, not the wrong scope.* Because shared framework libraries are non-singleton by default, two Apps in the *same* scope can run different patch/minor versions without a hard collision — that is the design. The default is not universal: the current Shell loader configs override selected Angular 21 / React 19 packages to `singleton: true`. What none of these settings rescues is a remote loaded into a scope that lacks a compatible provider for its framework: a scope mismatch can still become a load failure.
* *A shared library can be newer in the App than in the preloader.* The `requiredVersion` of a shared entry is the version the App declared in its own `package.json`, but the copy actually populated into the shared scope is the one the *preloader* bundles from its own dependencies (Unit 4). So a React 19 App built against a newer `@onecx/*` than the `react_19` loader bundles still declares that newer version as its `requiredVersion`, yet resolves the copy the loader provided. Because `strictVersion` defaults to `false` — and the `react_19` loader additionally forces `@onecx/*` to `singleton: true` — the version difference does not hard-fail the load; the App runs the preloader's (possibly older) copy and breaks only if it relies on newer `@onecx/*` APIs that copy lacks.
* *`configCallback` is a deliberate escape hatch.* An app can override the recommendations (for example forcing `singleton: true` on one package, or `includeSecondaries` for the `@angular-architects` toolchain). That is supported, but it makes that App's shared set diverge from the ecosystem default — a source of exactly the mismatches this Unit describes if done inconsistently.
* *Sub-package sharing depends on build-time resolution.* When `shouldGenerateSubDeps` is set, sub-packages are read from each dependency's `package.json` `exports`. If a package cannot be resolved in the build environment, it is skipped with a `[build-utils] Shared Config: skipping <dep>` log and its sub-packages are not shared.

== Debugging

* *Compare three scopes.* For a failing App, line up (1) the scope its packages were *built* into (the `shareScope` in its generated `shared` map), (2) the scope the Shell *loads* it with (the Workspace route's `shareScope`, via `toLoadRemoteEntryOptions`), and (3) the scopes the Shell *populated* (the preloaded loaders, Unit 4). The mismatch is always a disagreement between two of these.
* *Inspect the `Remote`.* The Shell loads an App with `{ type, entry, name, shareScope }` (Unit 2); `entry` is the remote URL and `shareScope` must name a populated scope.
* *Watch the console.* A preloader whose `loadRemote` rejected prints `Could not load preloader: <windowKey>` (Unit 4) — the most common signal that a scope is missing a compatible provider; a failed `loadRemote` of the App itself surfaces as a load error and routes to the Shell's remote-loading-error page (Unit 1).
