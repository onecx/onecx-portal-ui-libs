== Page Header Dynamic Actions Theming Analysis

=== Context

Page header actions are dynamic and may appear in any quantity.
Actions support:

* Variant: `button` and `link`
* Severity: semantic levels (for example: `primary`, `secondary`, `success`, `info`, `warning`, `danger`, `contrast`)
* States: `default`, `hover`, `active`, `focus`, `disabled`
* Size and ordering controls
* Runtime theme switching
* Flexible local overrides per action

=== Recommended Token Strategy

Define all action styling under `header.actionPanel` in the page-header usage schema.
Do not change primitives for this requirement.

Suggested structure:

* `header.actionPanel.layout`
** `gap`, `rowGap`, `columnGap`, `wrap`, `justifyContent`, `alignItems`
* `header.actionPanel.sizes`
** `sm`, `md`, `lg` token groups for spacing, icon size, font size
* `header.actionPanel.ordering`
** global order policy defaults
* `header.actionPanel.button`
** `defaultSeverity`
** `severity.<name>.{default,hover,active,focus,disabled}`
* `header.actionPanel.link`
** `defaultSeverity`
** `severity.<name>.{default,hover,active,focus,disabled}`

=== Resolution and Fallback

For each action, resolve styles in this order:

1. Action instance overrides (runtime config)
2. `header.actionPanel.<variant>.severity.<severity>.<state>`
3. `header.actionPanel.<variant>.defaultSeverity.<state>`
4. Existing primitive-driven defaults

This allows dynamic actions to be theme-consistent by default while remaining flexible.

=== Runtime Behavior

Runtime switching should be CSS-variable driven:

* Theme update publishes v2 tokens
* Variables are updated in the document root
* Header action styles consume variables only
* Dynamic actions restyle automatically without action-level rerender logic

=== Notes

* Keep API flexible: action config may provide `className`, inline style, and token override object.
* Keep theme-driven defaults first; use per-action overrides only for exceptions.
* Ordering can be a numeric value on action config; lower values render first.

=== Input

Accepted runtime input can be a single action object or an array of action objects.

[source,typescript]
----
const inputSingle = {
	id: 'save',
	variant: 'button',
	severity: 'primary',
	size: 'md',
	order: 10,
}

const inputArray = [
	{
		id: 'save',
		variant: 'button',
		severity: 'primary',
		size: 'md',
		order: 10,
	},
	{
		id: 'cancel',
		variant: 'link',
		severity: 'secondary',
		size: 'md',
		order: 20,
		disabled: false,
	},
]
----

=== Array Input to JSON Payload

Normalize to an array first, then serialize the final payload.

[source,typescript]
----
import { z } from 'zod'

const actionInput = z.object({
	id: z.string(),
	variant: z.enum(['button', 'link']),
	severity: z
		.enum(['primary', 'secondary', 'success', 'info', 'warning', 'danger', 'contrast'])
		.optional(),
	size: z.enum(['sm', 'md', 'lg']).optional(),
	order: z.number().optional(),
	disabled: z.boolean().optional(),
})

const oneOrManyActions = z
	.union([actionInput, z.array(actionInput)])
	.transform((value) => (Array.isArray(value) ? value : [value]))

const actions = oneOrManyActions.parse(input)

const payload = {
	usages: {
		pageHeader: {
			header: {
				actionPanel: {
					actions,
				},
			},
		},
	},
}

const json = JSON.stringify(payload, null, 2)
----
