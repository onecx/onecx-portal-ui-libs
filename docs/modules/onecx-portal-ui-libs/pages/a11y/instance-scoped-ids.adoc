[#instance-scoped-ids]
= Instance-scoped element ids

Several components render elements with fixed ids that are referenced by `for`, `aria-labelledby`, `aria-describedby` or `aria-controls`. When a component was used twice on one page, both instances rendered the same ids, so a label, description or controlled element could resolve to the other instance (WCAG 4.1.2, 1.3.1).

These ids are now unique per component instance.

[#instance-scoped-ids-rule]
== Rule

* The *first* live instance of a component keeps the existing (legacy) ids, for example `searchButton`.
* Every *further* live instance that exists at the same time gets a numeric suffix: `searchButton-1`, `searchButton-2`, ...
* When an instance is destroyed, its number is released and reused by the next instance.
* The numbering is kept per copy of `@onecx/angular-accelerator` in the browser. Two microfrontends that bundle their own copy number their instances independently, so their ids can still collide. The numbering is not meant for server-side rendering.
* All `for`/`aria-*` references inside a component use the same suffix, so they always point into their own instance.

Pages with one instance of a component are therefore unchanged.

[#instance-scoped-ids-migration]
== Migration

Nothing changes for pages that render each component once.

If a page renders a component more than once at the same time (for example two search headers, two interactive data views, or a dialog opened on top of another dialog), e2e tests and page objects that address the second instance by id must use the suffixed id, or match the id with a prefix:

[source,typescript]
----
// before: matched only the first instance
page.locator('#searchButton')
// after: any instance
page.locator('[id="searchButton"], [id^="searchButton-"]')
----

WARNING: The suffix depends on the order in which instances are created and destroyed, not on their position on the page. When the first instance is destroyed while a second one is still alive (for example a dialog that closes while the dialog below stays open, or a page section that is re-rendered), the second instance keeps its suffixed id, and the next instance that is created takes over the legacy id. An e2e test that addresses `#searchButton` can then hit a different instance than before. In e2e tests for pages with several instances, address an instance through a stable container (a `data-testid` or a parent element) and the prefix match above, not through a specific suffix.

The component harnesses of `@onecx/angular-accelerator/testing` match the legacy id and its suffixed variants, so harness-based tests work for every instance. For own harnesses, `@onecx/angular-accelerator/testing` exports:

* `instanceScopedId(id)`: a `RegExp` for the `id` option of harness predicates (the `id` option of `ButtonHarness`, `DivHarness`, `PButtonHarness`, `PButtonDirectiveHarness`, `PSelectHarness`, `PMultiSelectHarness` and `DataTableHarness` accepts `string | RegExp`).
* `instanceScopedIdSelector(id)`: a CSS selector for `locatorFor`. It matches by prefix (`[id="<id>"], [id^="<id>-"]`), so `instanceScopedIdSelector('page-header')` also matches other ids that start with `page-header-`. Use `instanceScopedId(id)`, which only accepts a numeric suffix, where that matters.
* `expectInstanceScopedIds(roots)` and `INSTANCE_ID_AXE_RULES`: test helpers that check that several instances on one page do not share ids and that no `for`/`aria-*` reference points into another instance.

[source,typescript]
----
import { expectInstanceScopedIds, INSTANCE_ID_AXE_RULES } from '@onecx/angular-accelerator/testing'
import { expectNoAxeViolations } from '@onecx/angular-testing'

expectInstanceScopedIds([first.nativeElement, second.nativeElement])
await expectNoAxeViolations(document.body, { rules: [...INSTANCE_ID_AXE_RULES] })
----

NOTE: Ids that the application passes in (custom dialog button ids, `primaryButtonDetails.id`, row ids, table names) are suffixed in the same way for further instances. Removing the legacy ids entirely is a separate, breaking decision for v9 GA.
